# 제품 검증 기준

[제품 명세](../product/spec.md)의 14장 기준. 인증·프로젝트 룸·MCP 요청·근거 판정과 계약 합의·변경·철회·폐기를 검증한다. 자동 검사의 성공을 첨부·실제 모델 호출·운영 기준의 완료로 해석하지 않는다. 기술·운영 정책은 [기술 설계](../product/technical-design.md)를 따른다.

## 현재 구성된 앱 기본 골격 검사

| 명령 | 확인 범위 |
|---|---|
| `npm run build`, `npm run typecheck`, `npm test` | 웹·API·MCP 빌드, 타입 및 DB 비의존 테스트 |
| `npm run test:integration` | 빈 시험 DB migration 뒤 health·probe·인증·프로젝트 권한·MCP 요청·근거·배경 작업 및 계약 합의·변경·철회·폐기·접근·동시성 통합 검사 |
| `npm run test:e2e` | 격리 브라우저·API·DB의 인증, 프로젝트 접근, MCP 요청·공개 회신·토큰 철회, 네 회원 계약 수정·동의·확정·변경·철회·폐기 공개 이력, health·probe 정상·장애·복구 |
| `pwsh -NoProfile -File scripts/check-harness.ps1` | 필수 문서·로컬 링크 검사. 제품 명령은 실행하지 않고 `PRODUCT: NOT_RUN` |
| `pwsh -NoProfile -File scripts/test-harness.ps1` | Harness 검사기의 격리 fixture와 제품 결과 전파 시나리오 |
| `pwsh -NoProfile -File scripts/check-product.ps1` 또는 `scripts/check-harness.ps1 -RequireProduct` | build → typecheck → test → test:integration → test:e2e; 하위 실패 코드 전달 |

두 격리 프로젝트의 실행기는 각자 생성한 시험 전용 volume의 정리를 시도하고 정리 실패를 보고한다. 개발 DB의 종료·초기화를 지시하지 않는다. [MCP Quickstart](../../specs/004-mcp-handoff/quickstart.md), [프로젝트 룸 Quickstart](../../specs/003-project-room-access/quickstart.md), [계약 Quickstart](../../specs/006-contract-agreement/quickstart.md)의 흐름을 확인한다. 자동 검사는 실제 Google·Discord OAuth 공급자 로그인, 첨부 권한, 실제 모델 API·비공개 GitHub 자격, Discord 알림, 운영 GCP 백업과 별도 환경 복구를 포함하지 않는다. 특히 R25는 시험 DB의 3회 보존만으로 통과 처리할 수 없다.

## 계약 수명주기 검증 추가

- migration0010의 기존 계약·응답 보존, A-only 변경/폐기, 사람 철회, 기준 확정본 재검사, 계약별 OPEN 하나, 실제 DB 잠금 경쟁 양쪽 순서를 검사한다.
- [변경·철회·폐기 Quickstart](../../specs/007-contract-lifecycle/quickstart.md)와 [실행 결과](../../specs/007-contract-lifecycle/validation.md)를 참조한다. R08/R13/R16 및 R19의 경쟁 변경안 부분을 구현하며, 담당자 복구·관리 종료는 남아 있다.

## 제품 기준 R01~R29

| ID | 기준 | 상태 |
|---|---|---|
| R01 | 승인된 사용자가 로그인 후 배정된 프로젝트를 선택하면 해당 공통 공간이 먼저 열린다. 미승인 사용자는 대기 화면만 본다. | 프로젝트 선택·빈 룸·대기 차단 E2E 검증. 요청 본문은 후속 |
| R02 | 팀원은 요청의 공개 제목과 게시된 회신을 열람한다. 비당사자는 요청 본문·첨부·비공개 버전을 열람할 수 없다. | 제목·회신 공개 및 본문·버전 비당사자 차단 통합·E2E 검증. 첨부 미구현 |
| R03 | 같은 프로젝트 팀원이어도 남의 초안이나 남의 응답 버튼에는 접근할 수 없다. | B 검토 초안은 B만 반환, 웹 회신 버튼 B만 표시. A의 전송 전 초안 저장 기능 미구현 |
| R04 | 수신자가 사람으로서 확인 완료를 선택하면 송신자 보낸함 상태가 갱신되고 알림이 생성된다. Codex의 사실 회신만으로 확인 완료가 되지 않는다. | 일반 인수인계의 사람 확인·보낸함·웹 알림 및 자동 회신과 상태 분리 통합·E2E 검증 |
| R05 | 수정 요청 의견이 원래 송신자에게 전달되고 재전송은 같은 요청의 새 버전이 된다. | 비공개 수정 의견·MCP 재전송·버전 이력 통합·E2E 검증 |
| R06 | 새 버전은 이전 확인을 승계하지 않고 재검토 대상으로 표시된다. | 새 버전 확인 대기, 이전 확인 기록 보존 및 재검토 집계 통합 검증 |
| R07 | 개발 계약에서 필수 PM의 동의는 확정 조건이며 참조 PM의 열람은 조건이 아니다. | A·B·필수 PM의 버전별 전원 동의, 참조자 미응답·이탈 비차단 통합 검사 및 최초 확정 E2E 검증 |
| R08 | 새 변경안 검토·수정·철회가 기존 확정본을 바꾸지 않는다. | 계약 수명주기 DB 검사에서 기존 포인터 보존, 전원 동의 후 교체 검증 |
| R09 | 오래된 화면에서 체크하거나 중복 클릭해도 잘못된 확정·중복 회신이 생기지 않는다. | 일반 요청 및 계약의 구버전409·재시도 중복 방지, 마지막 동의/재전송/수정/멤버 제외 경합 통합 검증 |
| R10 | 디스코드 장애 중에도 MCP 요청 전송과 웹 검토·처리를 계속할 수 있다. | 미구현/미검증 |
| R11 | 다른 팀·프로젝트의 API와 첨부 접근을 차단한다. | 프로젝트 룸 API 차단 통합·E2E 검증. 첨부는 미구현 |
| R12 | Codex 요청 전송·조회·근거 기반 사실 회신은 사람의 확인·계약 동의로 처리되지 않고, 연동 자격으로 그 상태 변경 API를 호출할 수 없다. | 사람 확인·계약 동의의 세션/CSRF 제한, MCP bearer 거부, 제안 직후 동의0건 및 MCP 동의 도구 부재 검증 |
| R13 | 철회와 마지막 동의를 동시에 시도하면 하나만 성공한다. 철회된 버전은 확정되지 않고, 확정된 버전은 철회되지 않는다. | 실제 DB lock 대기·양쪽 승리 순서를 강제한 통합검사 통과 |
| R14 | 수정 요청·확정·철회·관리 종료된 버전에는 새로운 응답을 저장하지 않는다. 동일 응답 재시도는 기존 결과만 반환하며 동의에서 수정 요청으로 바꾸는 호출은 거부한다. | 일반 요청과 계약의 종료 버전 응답 거부·동일 재시도 반환 검증. 계약 철회 구현·검증. 일반 요청 철회·관리 종료 미구현 |
| R15 | 송신자·수신자·필수 PM이 접근 권한을 잃으면 미완료 요청은 담당자 변경 필요가 된다. 관리 종료와 연결 요청 생성 후에도 이전 확인을 승계하지 않고 기존 확정 계약을 유지한다. 참조자 이탈은 검토를 막지 않는다. | 미구현/미검증 |
| R16 | 폐기 검토 중에는 기존 계약이 유효하며, 폐기 확정 후 웹·Codex의 유효 계약 목록에서는 제외된다. 직접 조회에서는 폐기 상태와 과거 기록을 구분해 보여준다. | RETIRED 현행 포인터 제거·MCP 유효 목록 제외·공개 이력 및 웹 과거 표시 검사 통과. 웹 전체 목록은 폐기 상태를 표시 |
| R17 | 서버 저장 직후 응답 유실을 재현하고 동일 전송을 재시도하면 요청·버전·알림 이벤트 수가 늘지 않는다. 다른 탭의 동일 초안 리비전 전송도 중복 발행되지 않는다. | 일반 요청과 계약의 동일 키 응답·전송/재전송·알림 중복 방지, PM 순서 정규화, 웹 오류 재시도 키·의견 보존 검증. 서버 저장 초안 리비전 미구현 |
| R18 | 수신자 동의 후 필수 PM만 대기하면 수신자의 확인 필요 건수는 0이고 전체 상태는 PM 확인 대기이다. 새 버전 전송 후에는 수신자의 재검토 필요 건수가 다시 증가한다. | 개인 동의와 전체 검토 대기 분리, 실행 가능한 최신 버전 집계 통합·웹·E2E 검증 |
| R19 | 같은 계약의 경쟁 변경안과 오래된 기준 확정본으로 합의를 시도하면 차단된다. 관리 종료 후 새 담당자의 연결 요청도 같은 계약 ID와 유효성 규칙을 유지한다. | OPEN 제안 하나·경쟁 변경안·오래된 기준 차단 및 철회 후 같은 계약의 새 제안 검증. 담당자 교체·관리 종료는 미구현 |
| R20 | Google·Discord 신규 가입자는 승인 전 프로젝트 조회·생성·첨부 다운로드 API를 사용할 수 없다. 서비스 관리자 승인 후에도 배정되지 않은 프로젝트에는 접근하지 못한다. | 프로젝트 조회·생성 및 미배정 차단 검증. 첨부는 미구현 |
| R21 | 승인 회원이 프로젝트를 생성하면 해당 프로젝트의 멤버·관리 담당자가 된다. 다른 프로젝트의 권한은 얻지 않는다. | 통합·E2E 검증 |
| R22 | 프로젝트 관리 담당자는 승인 회원만 자기 프로젝트에 추가·제외할 수 있다. 다른 프로젝트 멤버 변경·가입 승인·서비스 관리자 권한 부여 시도는 차단된다. | 프로젝트 멤버 변경 통합·E2E 검증. 서비스 권한 분리는 인증 통합 검사에서 확인 |
| R23 | 명시적으로 지정된 최초 관리자만 초기 관리자 권한을 받고, 서비스 관리자만 다른 승인 회원에게 그 권한을 부여한다. 관리자도 미배정 프로젝트의 본문과 남의 초안을 조회할 수 없다. | 초기 관리자·승격 및 미배정 룸 차단 검증. 본문·초안은 미구현 |
| R24 | 로그인 상태에서 다른 제공자를 연결하면 두 로그인 수단이 같은 승인 상태·프로젝트·받은함을 사용한다. 이메일 일치에 따른 자동 병합이나 다른 회원의 제공자 계정 덮어쓰기는 발생하지 않는다. | 계정 연결·동일 회원의 두 세션 프로젝트 목록 통합 검사. 일반 시험 회원의 실제 Google·Discord 재로그인 후 동일 프로젝트 목록 확인; 받은함 미구현 |
| R25 | 컨테이너를 교체해도 DB·첨부 데이터가 남으며, 하루 1회 외부 백업과 7일 보관 정책을 적용한다. 별도 환경에서 DB·첨부를 복구해 참조 정합성과 권한 있는 다운로드를 확인한다. | 미구현/미검증 |
| R26 | A의 Codex는 프로젝트별 MCP 권한으로만 B에게 요청을 자동 전송한다. 공개 제목과 비공개 본문·첨부를 분리하고 재시도에서 요청·버전이 중복되지 않는다. | MCP SDK·HTTP·E2E 전송과 재시도, 제목/본문 분리 검증. 실제 Codex 호스트 연결·첨부 미검증/미구현 |
| R27 | B의 PC가 꺼져도 서버가 세 가지 근거의 버전을 검사해 명시된 최신 사실만 팀에 자동 회신하고 중복 게시하지 않는다. | 확정 계약 현재 버전·등록 GitHub SHA·로컬24시간, 두 단계 수집/게시 직전 집합, 새 충돌/변경/폐기 양방향 PG lock wait, 중복 회신과 재확인 격리 DB·모의 Solar E2E 검증. 실제 Solar 새 흐름·PC 종료 운영 미검증 |
| R28 | 근거 부재·충돌·만료·추론·추천에서는 자동 공개 회신 없이 B 전용 검토 항목을 만들고, B가 웹에서만 최종 게시한다. | 한 줄 명시 문구의 누락·충돌·모호함·만료 단위/통합 검사, 계약 폐기 뒤 B 전용 검토·C 비노출 E2E 검증. 실제 AI 판정 정확도 미검증 |
| R29 | Codex 활동과 사람의 확인·동의는 별도 이력·권한으로 구분한다. 멤버십 제거와 MCP 연결 해제 후에는 조회·전송·배경 게시를 차단한다. | 서버 계약 수집 시 사람 감사/응답0건, 자동 회신 후 AWAITING_REVIEW 유지, grant/member/lease/키/사람 회신 경계 및 종료 요청 재실행 제외 검증 |

## 확정 계약 근거 연결 검증 추가

- [Quickstart](../../specs/008-contract-evidence/quickstart.md)와 [실행 결과](../../specs/008-contract-evidence/validation.md)를 참조한다. 모델 결과는 주입 모의이며 실제 공급자 시험과 구분한다.
- 단위 명령의 DB skip은 격리 migration DB 통합 결과로 보완한다. 계약의24시간 이전 확정본, 변경 검토/철회 동안 현행 유지, 다른 프로젝트/과거/폐기 제외, 정합성 실패를 검사한다.
- 사람 완료와 재확인 양쪽 실행 순서에서 job 상태를 보존하며, 모델/키/권한 실패를 계약 이벤트로 반복 호출하지 않는지 검사한다.
