# 작업 절차

1. [제품 명세](../product/spec.md), [기술 설계](../product/technical-design.md), [결정 기록](decisions.md), 현재 변경 사항을 확인한다.
2. 작업 목적·변경 파일·수용 조건과 [검증 기준](checks.md)의 관련 ID를 정한다.
3. [작업 양식](task-template.md)으로 `work/<task-id>/resume.md`를 만든다. 앱 구현 계획이 필요한 변경은 계획부터 마련한다.
4. 작은 변경 단위로 구현한다. 동작 변경은 관련 실패 사례를 먼저 재현하고 수정 후 검증한다. 단순 문서 수정에 형식적인 제품 테스트를 만들지 않는다.
5. 실제 검증 명령과 종료 코드를 기록한다. 미실행, 미설정, 실패, 성공을 구분한다.
6. 중요한 변경은 독립 리뷰를 받고 재현 조건을 확인해 지적을 반영한다.
7. 변경 내용·검증 증거·남은 작업을 보고한다. 완료 후 반복 사용할 결정만 [결정 기록](decisions.md)에 남긴다.

## 재개

재개 메모를 읽은 뒤 실제 파일·git 상태·검증 결과와 대조한다. 메모만 보고 이미 한 작업을 다시 수행하거나 테스트 성공을 추정하지 않는다.
다른 PC에서는 로컬 work 기록이 없으므로 공유 작업의 요약·커밋·검증 결과를 제공해야 한다.

## 현재 검증 범위

기본 Harness 검사와 자체 시나리오 검증만 가능하다. 앱 코드가 생기면 실제 테스트와 실행기를 함께 추가한다.
제품 검증 설정 플래그만 켜서 성공 처리하지 않는다. 외부 Discord 알림·제품 승인은 이 개발 절차의 자동 실행 항목이 아니다.

기술 스택은 확정돼 있다. 새 구현 시 선택을 임의로 바꾸지 말고, 미결정인 버전·도구·정책은 기술 설계의 확인 목록을 따른다. 제품 테스트·운영 Compose·DB 마이그레이션·복구 절차는 실제 파일과 실행 증거가 생기면 등록한다.
