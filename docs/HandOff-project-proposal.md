# HandOff 프로젝트 기획서

작성일: 2026-10-05 | 문서 버전: 1.0

기준: 제품 명세 v1.5, 기술 설계, 결정 기록 및 2026-09-30 / 2026-10-04 검증 기록. 이 문서는 기존 설계와 구현 상태를 정리한 기획서이며 신규 배포 또는 재검증 결과를 뜻하지 않는다.

## 1. 프로젝트 개요

| 항목 | 내용 |
| --- | --- |
| 프로젝트명 | HandOff |
| 프로젝트 타입 | 웹 기반 개발팀 협업 서비스. 소규모 팀을 위한 개발 계약·인수인계 관리 MVP |
| 도메인 | 개발 협업, 기술 합의 및 개발 계약 관리, 인수인계, AI 근거 검증 |
| 대상 사용자 | 4~5명 개발팀, 요청 송신자·수신자, 필수·참조 검토자, 프로젝트 관리 담당자 |
| 운영 도메인 | 서비스 DNS 도메인 미정. 현재 로컬 개발·검증 단계 |
| 현재 단계 | 인증·프로젝트·MCP 요청·사람 처리·계약 생애주기·근거 기반 자동 회신 구현. 운영 배포 준비는 후속 과제 |

### 기획 배경

Discord와 개인 대화에 흩어진 인수인계는 요청의 맥락, 수정 의견, 동의한 버전과 현재 유효한 규칙을 함께 추적하기 어렵다. 여러 작업자가 동일한 인터페이스나 규칙을 서로 다르게 이해하면 중복 질의와 재작업이 발생한다.

HandOff는 비공개 요청 처리와 팀 공개 결과를 프로젝트 룸 안에서 연결한다. Codex가 MCP로 요청을 전달하고, 사람은 확인·수정 요청·계약 동의를 수행한다. 모든 팀원은 공개 제목·공개 회신·확정 계약을 열람해 현재 합의를 공유한다.

여기서 계약은 API 응답 필드, 데이터 형식, 개발 책임 등 팀의 기술 합의다. 법률 계약이나 전자서명 서비스로 기획하지 않는다.

### 핵심 가치

1. Codex MCP로 요청 전송·재전송을 연결해 복사·붙여넣기를 줄인다.
2. 요청 본문과 수정 의견은 당사자에게, 공개 회신과 확정 계약은 팀에 공유한다.
3. 전송 버전과 동의 대상을 고정해 현재 유효한 합의를 식별한다.
4. 명시된 최신 근거가 있을 때만 자동 사실 회신하고 사람의 확인·동의와 구분한다.

## 2. 기술스택

아래 버전은 현재 저장소의 고정 버전 기준이다. 최신 시장 버전 또는 운영 배포 완료를 의미하지 않는다.

| 구분 | 선택 기술 | 적용 |
| --- | --- | --- |
| Front | React 19.3.0, TypeScript 5.9.3, Vite 8.3.0, MUI Material 9.4.0, Emotion | 반응형 웹, 프로젝트 메뉴, 카드·상태 배지, 공개 범위 표시 |
| Back | Node.js 24 LTS, NestJS 12.0.3, TypeScript, Express 어댑터 | REST API, 인증 세션·CSRF, 서버 권한 검증, 백그라운드 검증 실행기 |
| AI | Upstage Solar Pro 4 (`solar-pro4`), Chat Completions | 규칙 기반 사실 일치 검사 후 모델 재검사. 불확실하면 사람 검토 |
| Agent / MCP | Codex, Node.js·TypeScript stdio MCP 서버, MCP SDK 2.1.0 | 사용자·프로젝트별 위임을 받은 조회·요청·재전송·계약 제안 |
| DB | PostgreSQL 17.11, Prisma 7.10.0, PostgreSQL 어댑터 | 마이그레이션, 불변 버전, 상태 전환, 트랜잭션·중복 방지 |
| Deployment | GCP Compute Engine 서울 리전 `asia-northeast3`, Docker Compose, VM 영구 디스크, Cloud Storage | 운영 설계 확정. 실제 배포·HTTPS·백업 복구 검증은 미완료 |
| 개발·검증 | npm workspaces, Node.js 24, Docker PostgreSQL, Vitest, Testing Library, node:test, Playwright | 로컬 웹·API 실행, 단위·DB 통합·브라우저 E2E |

개발에서는 DB만 Docker로 실행하고 웹·API는 로컬 Node.js로 실행한다. 운영은 한 대의 GCP VM에서 웹·API·DB를 Docker Compose로 실행하는 계획이다. AI 호출은 서버에서 수행하며 사용자 브라우저에 모델 API 키를 제공하지 않는다.

### 권한과 열람 범위

- 미승인 회원은 프로젝트 조회·생성 불가. 승인 회원도 배정된 프로젝트만 접근한다.
- 서비스 관리자는 가입 승인을 담당하고 프로젝트 관리자는 자기 프로젝트 멤버를 관리한다. 관리자라는 이유만으로 비공개 요청 본문을 열람하지 않는다.
- 전송한 요청의 제목과 공개 회신은 프로젝트 팀원이 열람한다. 요청 본문·수정 의견은 송신자와 수신자만 열람한다.
- 검토 중인 계약 제안 본문은 지정 참여자만 열람한다. 확정된 계약 본문은 프로젝트 팀 전체에 공개한다.
- 전송한 버전은 불변이다. 수정은 새 버전으로 전송하며 기존 동의를 새 버전에 자동 적용하지 않는다.
- 내용 확인 완료는 읽고 검토했다는 표시다. 개발 작업 완료나 계약 동의를 의미하지 않는다.
- 에이전트는 사람의 확인 완료·계약 동의를 대신할 수 없다.

### 대표 흐름

인수인계: A의 Codex 요청 전송 → B의 비공개 검토 → 확인 완료 또는 수정 요청 → 필요 시 새 버전 재전송 → 공개 회신을 팀 피드에서 공유.

계약: 제안 → 지정 참여자의 검토·동의 → 같은 버전 전원 동의 → 팀 공개 확정 → 변경 제안 중에도 기존 확정본 유지 → 새 합의 또는 폐기 확정.

## 4. AI 자동 확인과 근거 정책

자동 확인은 새로운 추천이나 추측을 만드는 기능이 아니다. 요청에 포함된 `KEY: 값` 형식의 확인 항목을 명시된 최신 근거와 대조해 일치한 사실을 회신한다.

| 근거 | 유효 조건 | 주의 사항 |
| --- | --- | --- |
| HandOff 확정 계약 | 같은 프로젝트의 현재 활성 확정 버전 | 변경·폐기 뒤 과거 확정본은 현재 근거로 사용하지 않음. 24시간 TTL 적용 대상이 아님 |
| GitHub 저장소 파일 | 허용·등록된 읽기 전용 저장소와 조회 시점의 커밋 SHA | 저장소·파일 범위를 제한. 비공개 저장소의 실제 자격 증명 검증은 남아 있음 |
| 지정 로컬 계약 파일 | B가 지정한 파일을 성공적으로 동기화한 시점부터 24시간 이내 | 지정 파일만 전송. 변경 후 미동기화·유효 기간 만료는 근거에서 제외. DB에 AES-GCM 암호화 저장 |

처리 순서: 요청 권한과 최신 근거 확인 → 규칙 기반 값 일치·충돌 검사 → Solar Pro 4 재검사 → 게시 직전 버전·권한·근거 재검사 → 최소 사실 문장 공개 회신.

근거 부족, 오래된 로컬 파일, 충돌, 추론 필요, 모델 호출 오류 또는 권한 상실은 자동 공개 회신을 막고 B의 웹 검토로 넘긴다. 모델이 확인했다고 답해도 사람의 확인 완료·계약 동의 상태는 바뀌지 않는다.

서버 실행기가 백그라운드에서 동작하므로 수신자의 PC가 꺼진 상태에서도 서버에 있는 유효 근거를 사용할 수 있도록 설계했다. 실제 PC 종료와 장시간 운영 안정성은 별도 검증 과제다. 저장소 코드를 자동으로 수정하지 않는다.

| GCP / Cloud Storage | 운영 호스팅, 영구 데이터 저장, 일별 백업 | 설계 단계. 실제 배포·백업·복구 검증 필요 |

비밀 값은 서버의 .env 또는 보호 파일에 저장하고 문서·로그·Git에 넣지 않는다. 서비스 관리자만 AI 키를 입력·교체하며 저장된 원문은 다시 표시하지 않는다. OAuth 계정 연결은 사용자 본인의 명시적 인증으로 수행한다.

## 6. 개발·운영 계획

### 운영 아키텍처

- GCP 서울 리전 VM 한 대에 웹·API·DB를 Docker Compose로 배치한다.
- 첨부와 DB는 VM 영구 디스크에 보관한다. 첨부 기능 자체는 후속 개발 대상이다.
- 하루 1회 Cloud Storage에 백업하고 7일 보관하는 계획이다. 복구 실험 전에는 운영 준비 완료로 판단하지 않는다.
- 운영 도메인, HTTPS·리버스 프록시 제품, VM 사양, 컨테이너 레지스트리, CI/CD, 비용·복구 시간 목표는 별도로 확정한다.

### 남은 구현과 검증

1. 제품 완결: 첨부 업로드·열람 권한·다운로드·크기 제한, 담당자 이탈 시 이관과 계약 처리 복구, 관리자 이관·회원 비활성 정책.
2. 외부 알림: Discord 전달 방식, 연결되지 않은 사용자 처리, 재시도·실패 표시.
3. 운영 준비: 도메인·HTTPS·운영 OAuth, GCP 배포, CI/CD, 백업·다른 환경 복구 시험.
4. 안정성: 장시간 실행과 실제 PC 종료, 비공개 GitHub 자격 증명, 더 넓은 근거 오류·충돌 평가와 AI 호출 비용 관찰.
