# 개발 계약 합의 — 1단계 설계

상태: 사용자 설계·계획 승인 후 1단계 구현. 격리 환경에서 검증하며 운영 배포는 별도다.

## 목적과 승인된 방향

팀이 특정 개발 규칙에 누가 동의했는지 확인하고, 모두가 합의한 내용을 프로젝트의 현재 유효 계약으로 조회한다. 일반 인수인계의 ‘내용 확인 완료’와 계약 동의는 구분한다.

- 사용자는 합의 관리를 다음 기능으로 선택했고, 1단계 계약 생성·동의·최초 확정의 설계 문서 작성을 승인했다.
- 사용자 결정: **확정된 계약 본문은 현재 프로젝트 팀 전체에 공개**한다. 검토 중인 제안 본문과 수정 의견은 지정 참여자만 열람한다.
- 기존 [제품 명세](../../product/spec.md) 3·7·8장의 사람 동의, 버전 불변, 필수/참조 PM, 기존 확정본 유지 원칙을 따른다.
- 아래 API·데이터 구성과 세부 동작은 이번 문서의 검토 대상이다.

## 단계와 이번 범위

| 단계 | 범위 |
|---|---|
| **1 — 이번 구현** | MCP 계약 제안, 필수/참조 참여자, 사람 동의·수정 요청, 확정 전 새 버전, 최초 확정, 웹 알림·목록과 MCP 조회 |
| 2 | 확정 계약의 변경 제안·철회·폐기, 기준 확정본 및 경쟁 변경안 검증 |
| 3 | 담당자 이탈 복구, 관리 종료와 새 담당자의 연결 요청 |

이번 단계에서 확정 후 본문 변경·재전송·폐기 API는 제공하지 않는다. 기존 계약을 편집한 것처럼 보이게 별도 계약으로 자동 복제하지도 않는다. 확정 전 수정 요청에 대응하는 재전송은 포함한다. 필수 담당자의 권한 상실 시 응답·재전송은 첫 단계부터 차단한다.

첨부, Discord, 자동 판정기의 확정 계약 근거 연결, 검색·차이 비교, 서버에 저장하는 작성 초안은 후속 범위다. 명시적으로 API를 호출하기 전의 Codex 초안은 서버에 저장하지 않는다.

## 구현 접근 비교

1. **계약 전용 모델·API를 추가하고 공통 인증과 UI 관례를 재사용 — 권장.** 일반 인수인계의 확인과 계약의 다자 동의를 분리한다. 계약 전용 알림·목록이 추가되는 비용이 있다.
2. 기존 HandoffRequest에 유형과 모든 계약 상태를 통합한다. 화면·알림 재사용은 쉽지만 두 명을 전제한 권한, 응답, 자동 작업을 광범위하게 바꿔야 한다.
3. 별도 서비스로 계약을 분리한다. 독립 배포는 가능하지만 현재 4~5명 팀에 인증·트랜잭션·운영 복잡성이 크다.

1번을 제안한다. NestJS 앱과 PostgreSQL 내부의 계약 모듈로 구현하며, 기존 인수인계 API·기록·자동 회신 동작은 유지한다. 공통 잠금·회원 검증은 의미가 같은 부분만 재사용한다.

## 사용 흐름

1. A의 Codex가 프로젝트 범위의 MCP 권한으로 제목·제안 본문·B·필수 PM·참조 PM을 전송한다.
2. 계약 ID와 제안 요청 ID, 버전 1이 생성된다. A에게도 사람 동의가 필요한 항목이 생긴다. MCP 전송 자체는 동의를 만들지 않는다.
3. A·B·필수 PM은 웹에서 본문을 읽고 ‘이 버전에 동의’ 또는 ‘수정 요청’을 선택한다. 참조 PM은 열람만 한다.
4. 한 명이라도 수정 요청하면 버전 전체의 추가 응답을 닫고 A에게 수정 필요 알림을 보낸다. A의 MCP가 새 버전을 보내면 동의를 모두 새로 받는다.
5. 모든 필수 참여자가 동의하면 마지막 응답과 계약 최초 확정을 같은 트랜잭션에 저장한다.
6. 현재 프로젝트 멤버는 확정 계약 목록과 본문을 웹·권한 있는 MCP로 조회한다. 이전 검토 의견과 미확정 버전이 같이 공개되지는 않는다.

동의 버튼 주변에는 **‘전원 동의 시 이 버전의 본문이 프로젝트 팀 전체에 공개됩니다’**를 표시한다. 계약 본문은 확정 시 별도의 요약으로 바꾸지 않고 동의받은 그대로 공개한다. 수정 의견은 본문과 별도 필드다.

## 참여자와 열람 권한

- A와 B는 서로 다른 승인된 프로젝트 멤버다. 필수 집합은 A·B·선택한 필수 PM이다.
- PM은 프로젝트 권한과 무관한 해당 버전의 역할이다. 추가 필수/참조 PM은 각각 최대 10명이며, 모든 참여자는 중복·역할 겹침 없이 같은 프로젝트의 승인 회원이어야 한다.
- 주 송신자와 주 수신자는 이번 단계에서 고정한다. PM 구성은 확정 전 새 버전을 전송할 때 변경할 수 있으며 새 구성과 본문을 함께 고정한다.
- 비공개 버전은 현재 프로젝트 멤버이면서 **해당 버전의 참여자**인 사용자만 읽는다. 새로 추가된 PM에게 이전 비공개 버전을 자동 공개하지 않는다. 버전 목록도 읽을 수 있는 버전만 반환한다.
- 이전 버전에서 제외된 PM은 여전히 프로젝트 멤버라면 자신이 참여했던 과거 버전을 읽을 수 있으나 현재 검토에 응답할 수 없다.
- 참조 PM은 해당 버전 본문·검토 의견·처리 이력을 볼 수 있지만 동의·수정 요청 권한과 처리 필요 건수는 없다.
- 서비스·프로젝트 관리자도 참여자 요건을 건너뛰어 미확정 본문을 읽거나 다른 사람의 동의를 대행하지 못한다.
- 프로젝트 팀 공개 정보는 제안 제목·종류와 확정 후 본문·확정 시각이다. 비참여자에게 개인 동의 현황·참여자 ID·수정 의견·이전 비공개 버전을 반환하지 않는다.
- 프로젝트에서 제외되거나 가입 승인을 잃으면 공개 계약을 포함한 접근을 차단한다.

## 버전·응답·상태

계약의 상태는 `UNCONFIRMED` 또는 `ACTIVE`이며 현재 유효 버전 포인터를 별도로 둔다. 검토 버전 상태는 `IN_REVIEW`, `CHANGES_REQUESTED`, `SUPERSEDED`, `CONFIRMED`다.

| 현재 상태 | 동작 | 결과 |
|---|---|---|
| IN_REVIEW | 미응답 필수 참여자 동의 | 개인 응답 저장; 전원 동의 시 CONFIRMED 및 계약 ACTIVE |
| IN_REVIEW | 미응답 필수 참여자 수정 요청 | CHANGES_REQUESTED, 추가 응답 차단 |
| IN_REVIEW / CHANGES_REQUESTED | A의 새 버전 전송 | 과거 버전 SUPERSEDED, 새 버전 IN_REVIEW |
| CHANGES_REQUESTED / SUPERSEDED / CONFIRMED | 기존 버전에 새 응답 | 409; 동일 키·동일 내용의 재시도만 기존 결과 반환 |
| CONFIRMED | 새 버전 전송 | 이번 단계에서는 409; 변경 제안은 2단계 |

각 필수 참여자는 한 버전에 한 번만 응답한다. 동의 후 수정 요청으로 바꾸지 않는다. 의견은 수정 요청에 필수이며 1~10,000자다. 자동 회신·MCP 조회·알림 읽음은 동의가 아니다.

필수 참여자 중 한 명이라도 승인·멤버십을 잃으면 동의·수정 요청·재전송을 모두 차단하고 ‘담당자 변경 필요’를 표시한다. 권한 상실은 기존 응답이나 확정 기록을 지우지 않는다. 이 단계의 차단 표시는 현재 권한에서 계산하며, 전원이 권한을 회복하면 미확정 최신 버전의 검토가 다시 가능하다. 영구 종료·담당자 교체는 3단계에서 별도 상태와 이력으로 처리한다. 참조자의 이탈은 다른 사람의 검토를 막지 않는다.

개인의 확인 필요 건수는 응답 가능한 최신 버전의 필수 참여자 중 아직 응답하지 않은 사람에게만 1이다. 내가 동의했고 PM이 남으면 ‘내 동의 완료 / 전체 검토 대기’다. 수정 요청 상태에서는 모두의 확인 필요가 0이고 A의 수정 필요만 1이다. 권한 상실로 막힌 요청은 처리 가능한 건수에서 제외한다.

## 데이터와 원자성

- `DevelopmentContract`: 프로젝트, 공개 제목, UNCONFIRMED/ACTIVE, 현재 유효 버전 ID. 요청과 별도 ID를 가진다.
- `ContractProposal`: 계약 ID, A·B, 최신 검토 버전, 최초 전송 키/해시. 이번 단계에서는 계약당 하나다. 이후 단계에서 종료된 요청과 후속 요청을 연결할 수 있게 계약 ID를 독립시킨다.
- `ContractProposalVersion`: 제안 ID, 버전, 불변 본문, 상태, 생성/확정 시각, 전송 키/해시.
- `ContractParticipant`: 버전 ID, 회원 ID, SENDER/RECIPIENT/REQUIRED_PM/REFERENCE_PM. 버전·회원 조합은 유일하다.
- `ContractResponse`: 버전, 회원, AGREE/REQUEST_CHANGES, 의견, 응답 키/해시와 시각. 버전·회원당 하나다.
- `ContractNotification`: 개인 수신자, 제안·버전, 종류, 생성/읽음 시각. 동일 수신자·버전·종류는 중복되지 않는다.

모든 변경은 계약 행을 공통 기준으로 잠근 뒤 최신 버전·상태·필수 참여자 권한을 재검사한다. 회원/멤버십은 일관된 ID 순서로 잠가 제외와 확정이 동시에 승인되지 않게 한다. MCP 전송은 현재 grant도 재검사한다.

사람 응답·상태 변경·현재 유효 버전 갱신·알림은 한 트랜잭션이다. 전송 재시도는 같은 키·같은 내용에 같은 ID를 반환한다. 같은 키를 다른 내용에 쓰거나 예상 버전이 오래됐으면 409다. 참여자 배열은 ID 순서로 정규화해 동일 집합의 순서 차이가 다른 전송으로 처리되지 않게 한다.

두 동의가 동시에 와도 최초 확정과 확정 알림은 한 번만 저장한다. 수정 요청이 먼저 저장되면 후속 동의를 거부한다. 동의가 먼저라도 미응답 필수 참여자가 남아 있으면 그 사람의 수정 요청이 검토를 닫는다. 마지막 동의와 새 버전 전송이 경합하면 먼저 유효하게 저장된 명령 기준으로 다른 명령을 거부한다.

## 웹·API·MCP 경계

새 계약 API는 `/api/projects/:projectId/contracts`와 계약 제안 하위 경로로 분리한다. 사람 응답은 웹 세션+CSRF만 허용하고 MCP에는 응답 도구를 제공하지 않는다. UUID·정수 버전·길이·역할·중복을 서버에서 검증한다.

MCP 도구 제안:

- `propose_contract`: projectId, recipientId, publicTitle(1~160자), proposedBody(1~50,000자), requiredPmIds, referencePmIds, idempotencyKey(1~128자).
- `revise_contract_proposal`: proposalId, expectedVersion, proposedBody, requiredPmIds, referencePmIds, idempotencyKey. 아직 확정되지 않은 자기 제안만 새 버전으로 전송한다.
- `get_my_contract_proposal`: proposalId, 선택 version. 해당 버전 참여자의 조회만 허용한다.
- `list_active_contracts`: 연결된 프로젝트의 현재 유효 계약 목록. 미확정 계약은 제외한다.
- `get_contract`: contractId. 현재 팀원이 확정 본문을 읽으며, 내부 검토 데이터는 반환하지 않는다.

계약 본문 조회 이력은 동의 테이블과 분리해 회원·grant·버전·시각만 감사 기록한다. 조회는 읽었다는 기술적 사실이며 이해·준수·동의를 뜻하지 않는다. 목록 조회만으로 본문 조회 기록을 만들지 않는다.

웹은 프로젝트 룸에 ‘계약’ 진입점을 추가한다. 제목 목록과 확정 계약 상세는 팀원이 보고, ‘내 계약 검토’에서는 내가 참여한 제안·응답·알림을 본다. 제안 상세에는 현재 버전, 참여자별 동의 상태, 비공개 수정 의견, 내 동의/수정 버튼, 공개 예정 안내를 둔다. 과거 버전은 읽기 전용이다.

알림은 제안/새 버전 도착 시 현재 참여자에게, 수정 요청 시 A에게, 최초 확정 시 그 버전의 참여자에게 생성한다. 확정 계약 자체는 프로젝트 목록에 공개한다. 참조 알림은 읽을 수 있지만 할 일을 늘리지 않는다. 알림 payload에 본문·의견을 넣지 않으며 조회 시 현재 프로젝트 권한과 버전 참여를 검사한다.

네트워크 오류와 409 뒤 작성 중인 의견을 유지한다. 최신 버전을 다시 불러와도 의견을 자동 제출하지 않는다. 권한 없는 조회는 404, 인증 없음은 401, CSRF 없음은 403, 입력 오류는 400, 상태 충돌은 409다. 비공개 조회에는 no-store를 적용한다.

## 검증과 이전

신규 테이블 migration으로 시작한다. 기존 인수인계 확인을 계약 동의로 이전하거나 기존 요청을 자동 계약으로 바꾸지 않는다. 기존 자동 작업은 계약 동의를 생성하거나 변경하지 않는다.

필수 수용 시험:

1. MCP 제안 직후 A의 동의가 없고 A·B·필수 PM의 사람이 모두 동의해야 한 번 확정된다.
2. 참조 PM의 미확인은 확정을 막지 않으며 참조자·관리자·MCP 토큰의 동의 시도는 거부된다.
3. 비참여자 C는 검토 본문·응답을 읽지 못한다. 확정 후 정확한 확정 본문만 읽고 이전 수정 의견은 여전히 읽지 못한다.
4. B 동의 후 PM만 대기하면 B 할 일은 0이다. 수정 요청은 추가 응답을 닫고 새 버전은 모든 동의를 다시 받는다.
5. 버전에 새로 참여한 PM은 이전 비공개 버전을 읽지 못하며 참조자 이탈은 검토를 막지 않는다.
6. 동일 키 재시도, 다른 payload, 동시 마지막 동의·수정 요청·새 버전 전송·멤버 제외에서도 잘못된 확정과 중복 알림이 없다.
7. 미승인·미배정·제외된 회원의 본문·동의·MCP 조회를 차단한다. 확정 후 재전송도 차단한다.
8. 실제 DB 통합 및 A/B/필수 PM/비참여자 브라우저 E2E로 최초 제안→수정 요청→새 버전→전원 동의→팀 공개를 검증한다.
9. 기존 인증·인수인계·근거 자동 회신 검사를 유지하고 Node24 build/typecheck/unit/integration/E2E와 Harness를 실행한다. 실제 OAuth/Solar·운영 배포와 자동 검사를 구분한다.

## 자체 검토

- 계약 확정과 일반 확인을 분리했고 송신자 동의 누락, PM 집계, 비공개 과거 버전 노출을 명시적으로 다뤘다.
- 새 버전 전송은 확정 전으로 제한해 2단계의 확정 계약 변경을 우회하지 않는다.
- 사용자가 승인한 팀 공개는 확정 본문에만 적용한다. 미확정 의견·응답·참여 정보의 공개 확대는 하지 않는다.
- 담당자 복구와 계약 근거 자동 판정은 별도 후속 범위이며 이번 단계 완료로 표시하지 않는다.
