# 확정 계약을 자동 사실 회신의 근거로 연결

작성일: 2026-09-30
상태: 사용자 승인 설계 · 구현 및 자동 검증 완료 · 최종 리뷰 대기
기준: develop에 병합된 계약 합의·변경·철회·폐기 및 Upstage Solar Pro 4 사실 확인 경로

## 목적과 기존 합의

이미 팀이 합의한 개발 계약을 후속 인수인계 요청에서 재사용해 같은 사실을 반복 확인하는 일을 줄인다. 사용자가 다음 작업으로 이 연결을 선택했다. 현재 프로젝트의 유효 확정본만 사용하고, 변경 검토 중에는 기존 확정본을 유지하며, 폐기 계약은 자동 근거에서 제외한다.

기존 합의대로 자동 회신은 최신의 명시된 사실이 직접 일치할 때만 게시한다. 자연어 추론·추천, 근거 부족·충돌, 모델 실패는 B의 비공개 웹 검토로 넘긴다. 자동 사실 회신은 사람의 내용 확인 완료나 계약 동의가 아니다.

## 현재 코드에서 확인한 경계

- `EvidenceService.collect`는 수신자 B의 등록 로컬 파일과 GitHub 파일을 수집한다. `HANDOFF_CONTRACT` 타입은 있으나 확정 계약을 수집하는 구현은 없다.
- `decideReply`는 요청의 `verificationClaim`과 각 활성 근거의 `KEY: 값` 문구를 비교한다. 근거 누락·불일치·만료는 모두 검토 대상이다.
- 배경 작업은 결정적 비교 → Solar 확인 → 근거 재수집 → 게시 직전 권한·요청 버전·로컬 근거 검사 순서다. 현재 게시 검사의 근거 개수는 등록 파일 개수만 가정한다.
- 계약의 `ACTIVE/currentVersionId`는 최종 동의 트랜잭션에서 갱신된다. `RETIRED`의 현재 버전은 null이며 `lastConfirmedVersionId`는 과거 이력이다.
- 최초 합의와 변경·폐기 전원 동의는 계약 행을 잠근다. 프로젝트 전체의 근거 집합을 고정하는 잠금은 아직 없다.

## 선택지와 권장 방식

1. **같은 프로젝트의 현재 유효 계약을 자동 탐색한다 — 권장.** 별도 등록 없이 이미 공개된 합의를 재사용한다. 확인 키가 있는 계약만 비교하되, 동일 키를 가진 계약들의 충돌을 모두 검사해야 한다.
2. B가 계약을 하나씩 근거로 등록한다. 개인별 통제는 명확하지만 근거 등록 화면·저장 모델이 필요하고 새 합의가 등록에서 빠질 수 있다.
3. 요청이 특정 계약 ID를 지정한다. 추적은 쉬우나 요청 전송 도구의 입력이 늘고, 지정하지 않은 다른 유효 계약과의 충돌을 놓칠 수 있다.

이 검토안은 1번으로 설계한다. B의 현재 프로젝트 멤버십으로 이미 열람 가능한 팀 공개 계약을 자동 탐색한다. 다른 프로젝트나 미확정 제안, 비공개 의견은 탐색하지 않는다.

## 사실의 형식과 근거 선택

요청 예시: `verificationClaim: USER_ID_FORMAT: uuid-v4`

계약의 확정 본문에는 다음과 같이 명시한다.

```text
회원 식별자의 전달 형식에 관한 합의
USER_ID_FORMAT: uuid-v4
```

- 기존 키 형식 `[A-Z][A-Z0-9_.-]{1,63}`와 한 줄 값 길이 1~400자를 사용한다. 키·값의 대소문자와 의미를 임의 변환하지 않는다. 기존 파일 비교와 같은 한 줄 문법·공백 규칙을 공용 파서로 일치시킨다.
- 같은 프로젝트에서 `ACTIVE`이며 현재 버전이 신규·변경의 `CONFIRMED`인 계약만 후보로 읽는다. ID순으로 정렬하고 정확한 현재 버전 UUID를 기록한다.
- 요청과 같은 키의 문구가 없는 계약은 이 요청의 근거에 포함하지 않는다. 자연어만 적힌 계약에서 키·값을 추출하거나 만들어내지 않는다.
- 같은 키로 시작하는 줄이 있으나 유효한 한 줄 문법을 만족하지 않으면 모호한 근거로 검토에 넘긴다. 유효 줄과 잘못된 줄이 함께 있어도 자동으로 무시하지 않는다.
- 관련된 모든 계약의 해당 키 값이 요청과 같아야 한다. 동일 계약 안이나 서로 다른 계약에 다른 값이 있으면 검토 대상이다. 계약이 외부 파일의 불일치보다 우선한다는 규칙을 만들지 않는다.
- 로컬·GitHub 등록 근거의 기존 엄격한 비교·실패 규칙을 유지한다. 등록 파일에 키가 없거나 로컬 근거가 만료된 경우, 일치 계약이 있어도 자동 게시하지 않는다.
- 등록 파일이 없고 유효 계약만 있는 경우도 자동 후보가 될 수 있다. 관련 계약도 등록 파일도 없으면 근거 부족으로 검토한다.
- 계약은 서버의 현재 버전 조회로 최신성을 판단한다. 로컬 파일에만 적용하던 24시간 만료를 계약의 확정 시각에 적용하지 않는다. 오래전 합의도 여전히 유효하면 근거다.

## 수집·확인·게시 흐름

1. 최신 요청과 A/B의 승인·프로젝트 멤버십 및 A의 MCP grant를 검사한다.
2. B의 등록 파일과 프로젝트 유효 계약 중 확인 키의 후보를 수집한다. 계약 근거는 `kind=HANDOFF_CONTRACT`, `sourceId=계약 UUID`, `version=확정 버전 UUID`로 표현한다.
3. 결정적 검사에서 누락·모호함·충돌을 거른다. 통과한 실제 후보들만 기존 Solar Pro 4 확인기에 전달하며, 확인 키의 줄만 전송한다. 공급자·키 보관 방식은 유지한다.
4. Solar가 정상 확인한 뒤 같은 근거를 다시 수집한다. 근거 종류·ID·버전 및 후보 집합을 정렬해 비교한다. 관련 계약의 추가·교체·폐기나 파일 상태 변화가 있으면 게시를 중단한다.
5. 게시 트랜잭션에서 프로젝트 근거 집합과 요청을 잠그고 권한·실행 lease·최신 요청 상태를 다시 확인한다. 이 트랜잭션 안에서 관련 유효 계약 집합을 다시 읽고 이전 집합과 일치하는지 검사한다. 새 충돌 계약이 추가된 경우도 거부한다.
6. 등록 파일 검사와 계약 검사를 따로 수행한다. 등록 파일 개수와 모든 종류의 근거 개수를 비교하는 기존 가정을 제거하고, 파일 출처 변경·철회·로컬 해시·신선도 검사도 유지한다.
7. 기존 멱등 회신 키로 하나만 게시하고 실제 사용한 근거 참조를 작업 기록에 저장한다. 사람 회신·새 요청 버전·grant 철회·멤버 이탈은 기존 규칙으로 게시를 막는다.

공개 회신은 기존의 짧은 사실 확인 문구를 유지한다. 요청 본문·확인 키의 값·파일 경로·계약 원문을 자동 복사하지 않는다. 내부 근거 참조는 배경 작업 감사에 사용하며 공개 피드로 확장하지 않는다. 계약을 서버에서 읽은 일을 B의 사람 열람·동의 감사 기록으로 만들어내지 않는다.

## 변경·폐기와 게시의 동시성

계약별 행만 잠그면 확인 중 새로 확정된 다른 계약이 같은 키를 추가하는 경우를 막을 수 없다. 이를 위해 프로젝트별 PostgreSQL transaction advisory lock을 사용한다.

- 계약 저장소의 모든 변경 진입점은 동일 프로젝트의 배타적 근거 잠금을 **기존 계약 행·회원·grant·세션 잠금보다 먼저** 잡는다. 최초 확정·변경 확정·폐기에 따른 후보 집합 갱신을 함께 보호한다.
- 자동 게시 트랜잭션은 같은 프로젝트의 공유 근거 잠금을 **요청 행·회원·grant 잠금보다 먼저** 잡고, 최신 계약 집합을 재검사한 뒤 커밋까지 유지한다.
- 외부 파일 조회·Solar 호출은 이 잠금 밖에서 수행한다. 같은 프로젝트의 짧은 계약 쓰기만 직렬화하며 다른 프로젝트와 외부 호출을 막지 않는다.
- 변경·폐기가 먼저 커밋되면 오래된 집합으로 게시할 수 없다. 게시가 먼저 잠금을 얻어 유효한 집합으로 커밋하면 이후 계약 변경·폐기가 진행된다. 회신은 게시 시점의 사실 확인 기록이며 미래 계약 변경으로 삭제하거나 새 사실로 바꾸지 않는다.
- 복수 계약은 항상 ID순으로 읽고 참조를 정렬한다. 전체 잠금 순서를 통합 테스트에서 확인하며 DB deadlock을 단순 재시도로 숨기지 않는다.

새 근거 등록 모델·공개 API·DB migration은 기본 설계에 필요하지 않다. 기존 `evidenceRefs` JSON과 계약 모델을 사용한다. 구현 중 추가 모델이 꼭 필요하면 영향과 이유를 드러내고 설계를 갱신한다.

## 계약 확정 후 재확인

- 최초 확정·변경 확정·폐기가 실제 커밋될 때 같은 프로젝트에서 **근거 부족·누락·충돌·처리 중 근거 변경** 때문에 대기 중인 최신 요청의 서버 검토 작업만 재확인 대기로 돌린다. 불변 확인 키가 있는 요청에 한한다.
- 사람 확인·수정 요청으로 종료됐거나, 사람 공개 회신이 있거나, 자동 회신이 이미 게시된 요청은 재실행하지 않는다. 요청 버전과 실행 lease 검사를 유지한다.
- 근거를 바꾸지 않는 제안 전송·수정 요청·철회로 작업을 깨우지 않는다. 모델/키 실패·권한 실패 작업도 계약 변경만으로 반복 호출하지 않는다.
- 근거 변화가 커밋될 때 같은 조건의 실행 중 `PROCESSING` 작업도 기존 `executionId`·lease를 무효화하고 `PENDING`으로 돌린다. 이전 실행의 게시·검토 저장은 executionId 불일치로 거부한다. 새 실행은 갱신된 근거를 읽는다. 이 방식으로 실행 중 작업이 검토로 끝나는 시점 때문에 이벤트를 놓치지 않도록 검사한다.
- 최초 확정 전에 일치 근거가 없던 요청은 이후 확정된 계약을 검사할 수 있다. 기존 B의 미게시 검토 항목에 표시했던 근거 부족 사유는 새 실제 결과로 갱신하며, 공개된 사람 회신은 변경하지 않는다.

## 변경 단위

1. 공용 한 줄 파서와 계약 후보 수집·근거 참조.
2. 결정적 비교 및 기존 Solar 확인기 연결.
3. 계약 저장소·게시 경계의 프로젝트 잠금과 최신 집합 재검사.
4. 근거 변화에 따른 대기 요청 재확인 및 실행 중 경합 처리.
5. 자동 검사, 수동 실행 안내와 제품·기술·검증 문서 반영.

핵심 변경 대상은 evidence 서비스/파서, reply-decision, background-worker, contract repository와 관련 테스트다. 계약 편집 화면에는 자동 확인용 한 줄 형식 안내를 작은 도움말로 추가한다. API/MCP 입력 필드와 사람 동의·확인 규칙은 유지한다.

## 수용·검증 기준

- 계약만으로 명시 사실이 일치하면 회신 하나를 게시하고 정확한 계약·버전 UUID를 남긴다. 사람 확인·동의는 생성되지 않는다.
- 미확정·과거 확정본·폐기·다른 프로젝트 계약은 자동 근거가 아니다. 변경 검토와 철회 중에는 현재 확정본을 사용한다.
- 관계없는 계약은 방해하지 않는다. 관련 계약의 복수 값·다른 값·잘못된 같은 키 줄, 파일의 누락·만료·충돌은 자동 게시를 막는다.
- 자연어 요청/본문과 모델 실패는 B 전용 검토로 끝난다. 공개 피드에 비공개 원문·키 값·경로가 새로 노출되지 않는다.
- 모델 호출 중 변경·폐기·새 충돌 계약 확정, 게시와 최종 동의의 양쪽 승리 순서를 실제 PostgreSQL 잠금 대기로 강제해 검사한다.
- 근거 확정과 실행 중 검토 전환 경합에서도 최신 검사를 놓치지 않는다. 사람 회신·최신 버전·권한·grant·중복 실행 경계를 회귀 검사한다.
- 신규 파서/판정 단위, 격리 DB 수집·게시·재실행 통합, 사용자별 계약 확정→요청→자동 회신→폐기 뒤 새 요청 검토 E2E를 추가한다.
- Node24의 build/typecheck/test/integration/E2E와 Harness를 실제 실행한다. 기존 수동 앱·DB는 보존한다. 실제 Solar 호출은 사용자가 준비한 키를 보호한 별도 실연동 시험으로 구분한다.

## 이번 범위 밖

자연어 계약의 임의 구조화, 모델 추천·대리 동의, 계약별 수동 등록, 공개 근거 원문/경로 표시, 과거 자동 회신 삭제·상태 자동 갱신, 계약 검색·첨부·담당자 복구·외부 알림·운영 배포는 별도 작업이다.

## 자체 검토

- 목적은 기존 합의를 재사용하는 것으로 한정했다. 최신 상태, 중복 공개 방지, 사람 승인 구분을 보존한다.
- 계약의 최신성과 로컬 24시간 신선도를 구분했다. 관련 계약만 비교하는 예외와 등록 파일의 기존 엄격 규칙을 명시했다.
- 새 계약 확정으로 생기는 후보 집합 추가와 게시 경합을 프로젝트 잠금으로 다룬다. 기존 잠금보다 먼저 획득하도록 순서를 정했다.
- 재확인 이벤트를 실행 중 작업이 놓치는 경합을 수용 기준에 포함했다. 기존 executionId·lease를 무효화해 새 실행과 이전 실행을 구분한다.
- 설계와 구현 계획은 사용자 승인을 받았다. 구현·자동 검증 결과는 [검증 기록](../../../specs/008-contract-evidence/validation.md)에 분리하며, 실제 외부 모델 검증을 뜻하지 않는다.
