# 계약 변경·철회·폐기 설계

상태: 사용자 검토 전 설계안. 제품 코드 구현·마이그레이션 미실행.

## 목적과 확정 조건

최초 합의된 개발 계약을 안전하게 변경하거나 폐기하고, 미완료 제안을 사유와 함께 철회한다. 검토 중인 제안이 현재 유효 계약을 덮어쓰지 않아야 한다.

- 사용자 확정: 변경·폐기 제안은 기존 송신자 A만 시작한다.
- 기존 제품 규칙: A·B·필수 PM의 동일 버전 전원 동의가 필요하다. 참조 PM은 열람만 한다. 에이전트는 사람의 동의를 대행하지 않는다.
- 기존 제품 규칙: 확정 본문은 프로젝트 팀 전체 공개, 검토 본문과 수정 의견은 해당 버전 참여자만 열람한다.
- 이 문서에서 제안하는 세부 정책: 철회는 A가 웹에서 직접 사유를 입력한다. 폐기 이유는 폐기 합의가 끝나면 팀에 공개한다. 확정 전에는 참여자에게만 공개한다.

## 접근 방식

1. **기존 계약에 여러 제안을 연결한다 — 권장.** 현재 계약 ID와 확정 이력을 유지하고 기존 합의 로직을 확장한다. 현재 1:1 계약·제안 관계를 1:N으로 바꾸는 마이그레이션이 필요하다.
2. 변경마다 새 계약을 만든다. 구현은 작지만 같은 계약의 현행 버전과 폐기 이력을 추적하기 어렵고 제품의 동일 계약 ID 규칙과 맞지 않는다.
3. 별도 계약 서비스·이벤트 저장소를 만든다. 배포·동기화·운영 범위가 커져 현재 팀 규모에 불필요하다.

기존 NestJS 계약 모듈, PostgreSQL 트랜잭션, 웹 세션·CSRF, MCP 프로젝트 위임을 유지하는 1번을 적용한다.

## 사용자 흐름

### 변경

1. A의 Codex가 현행 확정본을 조회한다.
2. A의 프로젝트 MCP 권한으로 같은 계약 ID에 변경 제안을 전송한다. 기준 확정본 ID, 새 전체 본문, 필수·참조 PM, 재시도 키를 포함한다. A·B는 원래 계약의 당사자로 고정한다.
3. 참여자는 기존 확정본과 변경안 전체 본문을 구분해 검토한다. 자동 diff 생성은 이번 범위에 포함하지 않는다.
4. 수정 요청·재전송은 기존 버전 규칙을 따른다. 새 버전은 이전 동의를 승계하지 않는다.
5. 마지막 필수 동의 시 기준 확정본을 다시 검사한다. 유효하면 새 본문을 현행으로 교체하고 이전 확정본은 이력으로 보존한다.

### 철회

1. A가 웹의 자기 미완료 제안에서 현재 버전과 철회 사유를 확인하고 제출한다.
2. IN_REVIEW 또는 CHANGES_REQUESTED인 제안만 철회할 수 있다. 제안과 최신 버전은 WITHDRAWN이 된다.
3. 철회 후 새 응답과 같은 제안의 재전송은 차단한다. 과거 응답·버전·철회 기록은 보존한다.
4. 기존 확정 계약은 그대로 유효하다. 이어서 작업하려면 A가 이전 제안을 연결한 새 제안을 만든다. 최초 제안 철회 후에도 같은 계약 ID로 새 INITIAL 제안을 만들 수 있다.
5. 확정된 제안을 철회하는 기능은 없다. 확정 내용의 변경이나 폐기는 별도 합의를 거친다.

### 폐기

1. A의 Codex가 기준 확정본 ID와 폐기 이유를 넣어 RETIRE 제안을 전송한다.
2. 폐기 제안의 검토 본문은 폐기 이유다. 화면은 이를 새로운 계약 본문으로 표시하지 않는다. 수정 요청 후 새 버전으로 이유를 보완할 수 있다.
3. 검토 중에는 기존 계약이 계속 ACTIVE다.
4. A·B·필수 PM이 같은 버전에 모두 동의하면 계약을 RETIRED로 바꾸고 currentVersionId를 비운다. 마지막 확정 본문과 폐기 합의 버전·시각을 보존한다.
5. 팀 전체가 폐기 상태, 시각, 합의된 이유와 과거 확정본을 열람한다. 비공개 검토 의견·참여자 응답은 공개 DTO에 넣지 않는다.
6. 유효 계약 목록에는 나오지 않는다. 직접 조회에서는 `현재 유효 계약 없음`을 명시한다. 재활성화는 제공하지 않는다.

## 상태와 데이터

| 대상 | 추가·변경 |
|---|---|
| DevelopmentContract | RETIRED 상태, 원래 senderId·recipientId, lastConfirmedVersionId, retirementVersionId, retiredAt |
| ContractProposal | contractId의 unique 제거, kind INITIAL/CHANGE/RETIRE, lifecycle OPEN/CONFIRMED/WITHDRAWN, baselineVersionId, previousProposalId, 철회자·사유·시각·재시도 키·payload hash |
| ContractProposalVersion | WITHDRAWN 추가. 이미 전송된 본문·참여자는 변경하지 않음 |
| 알림 | 기존 확정 알림에 제안 종류를 반영하고 철회 알림 추가. 수신자·버전·종류 중복 방지 |
| 감사 | MCP 제안/재전송, 사람 응답/철회, 확정/폐기, 본문 조회를 식별 가능하게 보존 |

- 제안 번호와 버전 번호는 구분한다. 버전 번호는 각 제안 안에서 증가하며 비교·동의의 식별자는 불변 versionId다.
- 계약 하나에 OPEN 제안은 최대 하나다. DB 부분 unique index로 보장한다. CHANGES_REQUESTED도 OPEN에 포함한다.
- INITIAL은 UNCONFIRMED에서만, CHANGE·RETIRE는 ACTIVE에서만 시작한다. RETIRED에는 새 제안을 만들 수 없다.
- CHANGE·RETIRE의 baselineVersionId는 같은 계약의 현재 확정 본문 버전을 가리킨다. RETIRE 확정 버전은 현행 본문 포인터가 될 수 없다.
- 이전 제안 연결은 같은 계약의 WITHDRAWN 제안만 허용한다. 새 제안에는 동의를 복사하지 않는다.
- 새로 만드는 계약은 선택적인 이전 폐기 계약 링크를 받을 수 있다. 같은 프로젝트의 RETIRED 계약만 연결하며 권한을 승계하지 않는다.
- UNCONFIRMED는 현재·마지막 확정본이 없다. ACTIVE는 currentVersionId=lastConfirmedVersionId다. RETIRED는 currentVersionId가 없고 마지막 확정본과 폐기 합의가 있다.

## 권한과 경합

- A만 제안·재전송·철회할 수 있다. B·PM·프로젝트 관리자·서비스 관리자에게 이를 대행하는 권한을 주지 않는다.
- 모든 동작에서 현재 가입 승인, 프로젝트 멤버십, 해당 버전 참여 권한을 재검사한다. A·B·필수 PM의 접근 상실은 기존과 같이 담당자 변경 필요로 처리한다. 이 상태의 복구·관리 종료는 후속 범위다.
- MCP 제안은 현재 유효한 프로젝트 grant가 필요하다. 철회·동의·수정 요청은 사람 세션과 CSRF가 필요하다. grant로 사람 API를 호출할 수 없다.
- 계약 행을 먼저 잠근 뒤 상태, 현재 제안·버전, 기준 확정본, 멤버십과 세션/grant를 저장 직전에 검사한다. 기존 잠금 순서를 유지한다.
- 철회와 마지막 동의, 두 새 제안, 재전송과 철회가 경쟁하면 먼저 유효하게 저장된 동작만 성공한다. 후속 동작은 409와 최신 상태를 받는다.
- 동일 키·동일 payload의 재시도는 저장된 결과를 반환한다. 같은 키·다른 payload는 409다. 재시도 때도 현재 접근 권한을 검사한다.
- 과거 버전의 참여자라도 새 버전 본문을 자동으로 볼 수 없다. 공개 이력에는 확정 본문과 확정된 폐기 이유만 포함한다.

## API·MCP 변경안

| 경로/도구 | 용도 |
|---|---|
| 기존 POST `/api/mcp/contracts` / `propose_contract` | 최초 계약 생성 유지. 선택적 이전 폐기 계약 링크 추가 |
| POST `/api/mcp/contracts/:contractId/proposals` / `propose_contract_change` | CHANGE 또는 RETIRE 제안 생성. 기준 versionId 필수 |
| POST `/api/mcp/contracts/:contractId/proposals` / `restart_contract_proposal` | 철회된 INITIAL 이후 새 INITIAL 생성. previousProposalId 필수 |
| 기존 제안 versions API / `revise_contract_proposal` | 미완료 INITIAL·CHANGE·RETIRE의 버전 재전송 |
| POST `/api/projects/:projectId/contract-proposals/:proposalId/withdraw` | A의 웹 세션 전용 철회. expectedVersion·reason·idempotencyKey 필수 |
| 기존 사람 responses API | 제안 종류에 따라 최초 확정·본문 교체·폐기 처리 |
| 기존 계약 직접 조회와 `get_contract` | ACTIVE·RETIRED를 구별하는 DTO와 공개 확정 이력 제공 |
| 기존 `list_active_contracts` | ACTIVE만 반환하는 의미 유지 |

제안 생성 API는 kind별 필드 조합을 엄격히 검증한다. 접근 불가 대상은 404, 접근 가능한 오래된 상태·기준은 409, 유효하지 않은 grant는 기존 인증 정책을 따른다.

ACTIVE 직접 조회의 기존 version/body 필드는 유지한다. RETIRED에서는 현행 version/body를 null로 반환하고 lastConfirmed 및 retirement 필드로 과거 내용을 분리한다. 새로운 enum과 null을 웹·MCP 클라이언트에서 명시적으로 처리한다. 반환되지 않은 비공개 필드를 UI에서 숨기는 방식은 사용하지 않는다.

## 화면

- 계약 상세: 현행 확정본, 공개 확정 이력, 진행 중인 제안 유무를 구분한다. 참여자만 비공개 제안으로 이동한다.
- 제안 상세: 신규/변경/폐기, 기준 확정본, 제안 버전, 처리 상태를 표시한다. 폐기 동의는 `이 계약의 폐기에 동의`로 명시한다.
- A의 미완료 제안: 철회 사유 입력과 최종 제출 버튼. 재시도 중 입력·키 보존. 409 후 최신 상태 확인 없이 자동 재제출하지 않는다.
- 폐기 계약: 폐기 시각·이유·마지막 확정본에 과거 기록임을 표시하고 동의·재전송 버튼은 제거한다.
- 받은함·할 일·알림: 철회한 제안을 실행 가능한 검토 건수에서 제외한다. 개인 동의 완료와 제안 전체 확정 대기는 계속 구분한다.

## 마이그레이션과 검증

- 0010에서 기존 0009 데이터의 송신자·수신자, 제안 상태, 마지막 확정본을 채운 뒤 제약을 적용한다. 원래 제안 ID·버전 ID·응답·본문은 보존한다.
- 기존 UNCONFIRMED/ACTIVE, 수정 요청·재전송 이력이 있는 DB에 업그레이드하는 테스트를 작성한다. 실제 사용자 DB에 적용하기 전 백업·적용 대상을 확인한다.
- 정책·DB·HTTP·MCP·웹 검사: A 외 제안/철회 차단, grant의 사람 행동 차단, 기준 불일치, OPEN 중복, 철회 재시도, 비공개 이력 유출 차단, 제외 멤버·폐기 계약 접근.
- DB 경합: 실제 lock 대기를 관찰하고 양쪽 승리 순서로 철회/마지막 동의, 철회/재전송, 경쟁 제안을 검증한다. 응답·버전·알림 중복도 검사한다.
- E2E: 최초 확정 → 변경 검토·수정 → 철회(기존 본문 유지) → 새 변경 합의(본문 교체) → 폐기 합의(유효 목록 제외·직접 조회 이력)를 A/B/PM/C로 검증한다.
- 최종 build·typecheck·단위·통합·E2E와 기존 인수인계 회귀 검사를 실행한다. 로컬 환경만으로 실제 OAuth·Solar·운영 복구 성공을 주장하지 않는다.

## 범위 밖

담당자 교체·관리 종료, 첨부, Discord 외부 알림, 계약을 자동 판정 근거로 등록하는 기능, 운영 배포는 별도 작업이다. 이번 문서의 작성은 이 기능들이 구현됐다는 뜻이 아니다.
