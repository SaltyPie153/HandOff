# 일반 인수인계의 사람 처리 흐름

작성일: 2026-09-29
상태: 구현 전 설계 검토
기준: develop 병합 커밋 `56419a0`

## 목적과 범위

사용자가 선택한 다음 기능은 수신자의 확인 완료, 수정 요청, 송신자의 새 버전 재전송, 송신자 상태 알림이다. 기존 [제품 명세](../../product/spec.md)의 일반 인수인계 규칙을 구현한다. 공개 회신을 게시한 사실과 사람이 요청 내용을 확인한 사실을 각각 기록한다.

수용 시나리오: A의 Codex가 B에게 v1을 전송한다. B가 웹에서 비공개 수정 의견을 남기면 A의 보낸함에 수정 필요와 알림이 표시된다. A의 Codex가 같은 요청에 v2를 전송하면 B가 재검토하고 확인 완료한다. A는 v2의 확인 완료 알림을 본다. C는 공개 제목과 게시된 공개 회신만 볼 수 있다.

이번 범위는 일반 인수인계다. 개발 계약의 송신자·PM 동의, 계약 확정·폐기, 담당자 관리 종료, 첨부, Discord 발송은 후속 기능이다. 웹 알림은 이번에 포함한다. 새 버전 전송은 기존 정책대로 송신자의 MCP 연결을 사용한다.

## 현재 코드에서 확인한 점

- `HandoffRequest`에 요청 처리 상태가 없고 `HandoffVersion`은 본문과 자동 확인 문구만 보관한다.
- `HandoffReply`는 요청에 연결되어 있고 버전 식별자가 없다.
- `HandoffJob`은 요청당 한 행이다. 이전 공개 회신이 하나라도 있으면 새 자동 처리를 생략한다.
- 상세 조회는 최신 버전 하나만 반환한다. 받은함과 보낸함은 같은 목록에 방향만 표시한다.
- 공개 회신 게시 API는 세션과 CSRF를 사용한다. MCP에는 전송과 조회 도구만 있다.

## 접근 방식

| 방식 | 영향 | 판단 |
|---|---|---|
| 기존 요청·버전에 사람 응답과 웹 알림을 추가 | 현재 MCP와 화면을 재사용하며 필요한 버전 경계를 보강 | 채택 |
| 별도 업무 처리 서비스 신설 | 인증·권한·상태 동기화가 중복됨 | 이번 규모에 불필요 |
| 계약 합의·PM·Discord까지 함께 구현 | 검증 범위와 미결정 정책이 크게 늘어남 | 후속 단위로 유지 |

## 사용자 흐름과 상태

수신자는 최신 버전의 확인 대기 상태에서 웹으로 두 동작 중 하나를 수행한다.

- **내용 확인 완료**: 해당 버전을 읽고 확인했다는 기록. 후속 개발 완료나 계약 동의가 아니다.
- **수정 요청**: 필수 의견을 입력한다. 의견은 A와 B만 읽으며 팀 공개 회신으로 자동 게시하지 않는다.

| 현재 버전 상태 | 동작 | 결과 |
|---|---|---|
| 확인 대기 | B의 확인 완료 | 확인 완료, 응답·A 알림을 함께 저장 |
| 확인 대기 | B의 수정 요청 | 수정 요청됨, 응답·A 알림을 함께 저장 |
| 확인 대기 또는 수정 요청됨 | A의 MCP 재전송 | 이전 버전은 대체됨, 새 버전은 확인 대기 |
| 확인 완료 | A의 MCP 재전송 | 이전 확인 기록 보존, 새 버전은 확인 대기 |
| 응답됨 또는 대체됨 | 기존 버전에 새 응답 | 거부 |

같은 응답을 재시도하면 기존 결과만 반환한다. 확인 완료를 수정 요청으로 바꾸는 응답 변경은 거부한다. 새 버전에 이전 확인을 승계하지 않는다. 오래된 화면의 버전으로 응답하거나 재전송하면 충돌로 안내한다.

공개 회신은 별도 기능으로 유지한다. 과거 버전의 회신도 팀에 남기되 버전을 표시한다. 사람이 최신 버전에 확인 완료나 수정 요청을 저장하면 해당 버전에서 진행 중인 자동 작업을 무효화한다. 새 버전에는 새로운 자동 확인 작업이 생긴다.

## 데이터와 마이그레이션

- 버전에 `AWAITING_REVIEW`, `ACKNOWLEDGED`, `CHANGES_REQUESTED`, `SUPERSEDED` 상태를 둔다. 전송된 본문·자동 확인 문구는 수정하지 않는다.
- 요청에는 최신 버전 번호를 두고 트랜잭션에서 새 번호를 발행한다.
- 사람 응답은 별도 테이블에 버전, 수신자, 동작, 비공개 의견, 시각, 재시도 키와 payload 해시를 저장한다. 버전별 수신자 응답은 하나로 제한한다.
- 재전송의 키와 payload 해시를 저장해 응답 유실 후 재시도에도 버전과 알림이 증가하지 않게 한다.
- 공개 회신과 배경 작업에 버전 연결을 추가한다. 배경 작업의 기본 식별도 버전 기준으로 바꾼다.
- 웹 알림에 수신 회원, 프로젝트, 요청, 버전, 이벤트 종류, 생성 시각, 읽은 시각을 보관한다. 이벤트별 수신자 알림을 유일하게 한다. 비공개 의견과 본문을 알림에 복제하지 않는다.
- 기존 요청은 사람의 응답 기록이 없으므로 확인 대기로 시작한다. 기존 `HandoffJob.COMPLETED`나 공개 회신을 사람 확인으로 변환하지 않는다. 기존 공개 회신·작업은 현재 단일 버전인 v1에 연결한다. 기존 버전이 여러 개인 데이터가 있으면 임의 연결하지 않고 마이그레이션 전 점검에서 차단한다.

## API와 MCP 경계

- `POST /api/projects/:projectId/requests/:requestId/responses`: 웹 세션+CSRF, `version`, `action`, `comment`, `idempotencyKey`. B만 호출 가능하다. MCP bearer만으로 호출할 수 없다.
- 기존 상세 API: 최신 상태와 허용 동작, 버전별 응답 이력 추가. `GET .../requests/:requestId/versions/:version`으로 과거 본문을 A·B에게만 제공한다.
- `POST /api/mcp/requests/:requestId/versions`: 송신자 MCP 권한, `expectedVersion`, `privateBody`, 선택적 `verificationClaim`, `idempotencyKey`. 프로젝트·송신자·수신자를 변경하지 않는다. 공개 제목도 이번 재전송에서 유지한다.
- MCP 도구 `resend_request` 추가. 기존 `get_my_request`로 현재 버전·비공개 수정 의견을 확인할 수 있다. 사람 응답 도구는 추가하지 않는다.
- 기존 inbox API에 방향별 필터와 상태·할 일 집계를 추가한다. 기존 배열 응답과 호환되게 집계는 별도 endpoint로 제공한다.
- 프로젝트 내 개인 알림 목록과 단건 읽음 API를 추가한다. 자신의 알림만 반환하며 조회 시에도 현재 프로젝트 접근 권한을 확인한다.

입력 길이·UUID·버전·동작 enum을 검증한다. 수정 요청 의견은 1~10,000자다. 무권한 상세는 기존처럼 404, 세션·CSRF 위반은 기존 인증 정책, 오래된 버전이나 상태 충돌은 409로 반환한다.

## 동시성과 자동 회신

요청 행을 공통 잠금 기준으로 삼아 사람 응답, 재전송, 자동 게시를 직렬화한다. 저장 직전 최신 버전·응답 상태·프로젝트 접근을 재검사한다. 사람 응답·버전·알림 생성은 하나의 트랜잭션이다. 공개 회신의 사람/자동 출처는 사람 응답 테이블과 분리한다.

자동 작업은 시작 시 선택한 버전에 고정한다. 게시 직전에 같은 버전이 여전히 최신 확인 대기인지 검증한다. 이전 버전에서 생성된 실행 결과를 새 버전에 게시하지 않는다. 기존 사람 공개 회신 때문에 자동 게시를 생략하는 동작은 해당 버전 안에서만 적용한다.

새 버전 전송 시 A·B 모두 승인된 프로젝트 멤버여야 한다. 사람 응답도 두 담당자의 접근 가능 여부를 확인한다. 멤버 이탈 후 관리 종료·새 담당자 연결 기능의 전체 수명 주기는 후속 범위로 명시한다.

## 웹 화면

- 받은함·보낸함을 탭 또는 필터로 구분한다. B는 확인 필요/내 응답 완료, A는 상대 확인 대기/내 수정 필요/확인 완료를 본다. 새 버전은 재검토로 표시한다.
- 상세에 현재 버전 상태, B의 사람 응답과 시각, 비공개 수정 의견을 표시한다. 공개 회신 입력과 사람 처리 버튼은 별도 영역이다.
- 과거 버전은 읽기 전용이며 응답 버튼을 표시하지 않는다. 오래된 상태로 저장하면 최신 버전을 다시 확인하도록 안내하고 입력한 의견은 보존한다.
- 프로젝트 룸과 개인 공간에서 미확인 알림·확인 필요·수정 필요 수를 확인한다. 알림 읽음은 요청 확인 완료를 의미하지 않는다.
- 재전송은 A가 Codex에 요청하도록 현재 request ID와 버전 안내를 제공한다.

## 검증과 완료 기준

관련 기준: R04~R06, R09·R12·R14의 일반 인수인계 부분, R17·R29.

1. 확인 완료/수정 요청은 정확한 버전·회원으로 한 번 저장되며 웹 알림도 한 번만 생성된다.
2. 수정 의견은 A·B만 읽고 C의 공개 피드·상세·알림 API에는 노출되지 않는다.
3. MCP·다른 회원·잘못된 프로젝트·CSRF 없는 요청으로 사람 응답을 할 수 없다.
4. 재전송 후 이전 본문과 응답은 보존되고 B는 새 버전을 다시 확인해야 한다.
5. 동일 재전송 키는 같은 결과, 다른 payload는 충돌을 반환한다. 동시 재전송·사람 응답 경쟁에서도 유효한 상태만 저장된다.
6. 지연된 v1 자동 실행이 v2에 게시되지 않는다. v1 공개 회신이 있어도 v2의 자동 확인은 가능하다.
7. 기존 데이터 migration 및 A→B 수정 요청→MCP v2→확인 완료→A 알림을 격리 DB와 세 사용자 E2E로 검증한다.
8. Node24 build/typecheck/unit/integration/E2E와 Harness 검사를 실행한다. 개발 DB·기존 로컬 앱과 포트가 겹치면 기존 프로세스를 종료하지 않고 시험 환경의 포트를 분리한다.

2026-09-29: 승인 후 구현 및 격리 DB·E2E 검증을 완료했다. 기존 개발 DB와 실행 중인 앱에는 적용하지 않았다. 실행 기록은 [구현 계획](../plans/2026-09-29-handoff-human-workflow.md)의 결과 절을 참고한다.
