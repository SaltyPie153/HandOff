# 개발 계약 및 인수인계 웹서비스 — 첫 버전 제품 명세

작성일: 2026-09-21
상태: 기술·가입·운영 정책 반영본 v1.2 · 구현 전
대상: 각자 PC에서 Codex를 사용하는 4~5명 개발팀

개정 사항: v1.1의 상태·동시성 규칙을 유지하고, 확정 기술 스택·소셜 가입 승인·프로젝트별 권한·VM 운영과 백업 정책을 반영했다. 세부 기술 결정은 [기술 설계 및 운영 결정](technical-design.md)을 참조한다.

## 1. 목적과 제품 방향

디스코드에 수동으로 복사해 전달하던 개발 계약과 인수인계를 웹서비스에서 관리한다. 누가 어떤 버전을 확인했는지, 무엇이 확정됐는지, 누구의 응답이 필요한지 추적한다. 임시 Handoff 파일을 코드 저장소에 계속 추가할 필요를 줄인다.

제품의 핵심 가치는 ‘프로젝트 팀이 같은 기록을 보고, 담당자가 자기 요청을 쉽게 처리하며, 회신이 원래 보낸 사람에게 자동으로 돌아오는 것’이다.

우선 내부 팀에서 사용하고 실제 문제를 보완한 후 공개 서비스로 확장한다. 첫 버전은 Google·Discord 로그인으로 가입 신청을 받고 서비스 관리자 승인 후 이용한다. 자동 승인되는 공개 서비스 가입·결제·요금제는 포함하지 않는다.

## 2. 합의된 요구사항과 설계 제안

### 사용자와 합의된 요구사항

- 첫 화면은 프로젝트 선택 화면이다.
- 프로젝트마다 팀 공통 공간이 있고, 그 안에서 자신의 개인 공간으로 이동한다.
- 프로젝트 팀원은 전송된 요청의 본문까지 열람할 수 있다.
- 담당자는 기본적으로 정해져 있다. 각 요청의 주된 송신자와 수신자는 1:1이다.
- 개발 계약과 일반 인수인계를 모두 다룬다.
- Codex가 초안을 작성하고 사람이 검토한 뒤 전송한다.
- 담당자가 검토 후 체크하면 원래 송신자에게 자동 회신한다.
- 수정 요청과 의견 전달을 지원한다.
- 개발 계약은 양쪽 담당자가 확인하며, 필요하면 PM이 필수 확인 또는 참조로 참여한다.
- 디스코드를 알림 창구로 사용한다.
- Google·Discord 로그인을 지원하고 가입 후 서비스 관리자가 승인한다. 로그인한 상태에서 다른 로그인 수단을 직접 연결하며 이메일 기반 자동 병합은 하지 않는다.
- 승인 회원 누구나 프로젝트를 생성하고 생성자가 프로젝트 관리 담당자가 된다. 프로젝트별 멤버 배정 후 접근하며 프로젝트 관리 담당자도 승인 회원을 자기 프로젝트에 추가·제외할 수 있다.
- 최초 서비스 관리자는 사용자 본인으로 명시 지정하고, 이후 서비스 관리자가 다른 승인 회원에게 관리자 권한을 부여한다.

### 이 명세에서 구체화한 제안

아래는 구현 가능한 동작을 정의하기 위한 제안이며, 이번 문서 검토 대상이다.

- ‘세션’의 화면 명칭은 ‘공통 공간’과 ‘내 공간’으로 한다. Codex 대화 세션과 무관하게 기록을 유지한다.
- 전송한 버전의 본문과 첨부는 수정하지 않고 새 버전을 발행한다.
- 개발 계약 송신자는 전송 시 해당 버전에 대한 동의를 명시한다.
- 변경안 검토 중에는 기존 확정본이 계속 유효하다.
- 일반 인수인계의 확인은 수신·검토 확인이며 후속 개발 완료가 아니다.
- 초안은 작성자에게만 공개한다. 전송된 기록은 프로젝트 팀원 전체가 열람한다.
- PM은 같은 요청의 추가 확인자 또는 참조자로 연결한다. 주 송신자·수신자 관계는 그대로 유지한다.
- 미완료 검토안은 삭제 대신 철회하며, 철회 이유와 이력을 보존한다. 확인·확정 완료된 버전은 철회하지 않고 새 변경안으로 처리한다.

## 3. 사용자와 권한

첫 내부 운영에서는 승인 회원이 하나의 팀에 속하고 프로젝트별로 배정된다. 서비스 가입 승인과 프로젝트 멤버십은 별개의 권한이다. 담당자와 PM은 요청별 역할이며 PM에게 자동으로 서비스·프로젝트 관리 권한을 주지 않는다.

| 역할 | 할 수 있는 일 |
|---|---|
| 승인 대기 회원 | 승인 대기 화면 확인. 프로젝트 목록·본문·첨부 조회와 프로젝트 생성 불가 |
| 승인 회원 | 프로젝트 생성. 기존 프로젝트는 별도 배정 후 접근 |
| 서비스 관리자 | 가입 승인, 다른 승인 회원에게 서비스 관리자 권한 부여, 승인 회원의 프로젝트 배정 |
| 프로젝트 관리 담당자 | 생성자로서 자기 프로젝트 관리, 승인 회원 추가·제외, 해당 프로젝트의 담당자 이탈 요청 관리 종료 |
| 프로젝트 팀원 | 프로젝트 내 전송된 모든 요청의 본문·첨부·버전·회신 열람, 요청 작성 |
| 송신자 | 자기 초안 편집·전송, 수정안 작성·재전송, 미완료 검토안 철회 |
| 주 수신자 | 자신에게 지정된 버전 확인·동의 또는 수정 요청 |
| 추가 필수 확인자 | 지정된 개발 계약 버전에 동의 또는 수정 요청 |
| 참조자 | 열람 및 알림 수신. 미확인 상태가 확정을 막지 않음 |

권한은 서버에서 검증한다. 서비스 관리자도 콘텐츠를 열람하려면 해당 프로젝트에 배정돼야 한다. 프로젝트 관리 담당자는 다른 프로젝트의 멤버나 서비스 가입 승인을 변경하지 못한다. 다른 사람의 개인 공간을 대신 조작하거나 URL만으로 프로젝트 자료를 조회할 수 없으며, 어떤 관리자도 다른 담당자의 동의를 대신 처리하지 않는다.

### 가입과 계정 연결

- 최초 Google 또는 Discord 로그인 후 승인 대기로 등록한다. 승인 전에는 프로젝트에 접근할 수 없다.
- 최초 서비스 관리자는 배포 설정으로 사용자 본인 계정을 명시 지정한다. 첫 로그인 사용자를 임의로 관리자로 만들지 않는다.
- 로그인한 회원이 다른 제공자 인증을 완료해 기존 회원 계정에 연결한다. 이메일 일치만으로 계정을 자동 합치지 않는다.
- 연결된 로그인 수단은 동일한 내부 회원 ID, 가입 승인, 프로젝트 멤버십, 받은함을 사용한다. 다른 회원에게 이미 연결된 계정은 덮어쓰지 않는다.
- 프로젝트를 생성하면 생성자를 해당 프로젝트 멤버·관리 담당자로 함께 등록한다. 승인됐다는 이유만으로 다른 모든 프로젝트에 배정하지 않는다.

첫 버전에서는 전송 후 주 송신자·수신자를 바꾸지 않는다. 잘못 지정한 요청은 철회하고 올바른 대상에게 새 요청을 보낸다. 필수 확인자 구성 변경은 새 검토 버전에 기록하고 다시 확인받는다.

### 담당자 이탈 복구

- 미완료 요청의 송신자·주 수신자·필수 PM이 비활성화되거나 프로젝트 접근 권한을 잃으면 요청을 ‘담당자 변경 필요’로 전환하고 일반 응답·재전송을 막는다. 참조자 이탈은 검토를 막지 않는다.
- 해당 프로젝트 관리 담당자 또는 그 프로젝트에 배정된 서비스 관리자는 종료 사유를 기록해 해당 미완료 요청을 ‘관리 종료’로 바꿀 수 있다. 관리 종료는 확인·동의·계약 폐기를 뜻하지 않는다.
- 프로젝트 팀원인 새 담당자는 전송된 원문을 바탕으로 새 요청을 작성하고 이전 요청 ID를 연결한다. 관리자는 이전 담당자의 개인 초안을 열람하거나 승인 기록을 대신 만들 수 없다.
- 이전 요청과 새 요청은 양방향 링크로 표시하고, 이전 동의·확인은 승계하지 않는다. 권한 복구만으로 종료 요청을 자동 재개하지 않는다.
- 이미 확인 완료된 인수인계와 확정된 계약은 담당자 이탈로 상태가 바뀌지 않는다. 미완료 변경안을 관리 종료해도 기존 확정본은 계속 유효하다.
- 기존 확정 계약의 담당자 교체가 필요하면 같은 계약에 연결된 새 요청에서 새 담당자들이 재확인한다. 이 새 버전이 확정될 때까지 기존 확정본을 유지한다.

## 4. 화면과 이동 구조

```text
로그인
├─ 승인 대기 회원: 승인 대기 화면
└─ 프로젝트 선택
   └─ 프로젝트 공통 공간
      ├─ 전체 요청 목록
      ├─ 요청 상세
      └─ 내 공간
         ├─ 받은함
         ├─ 보낸함
         └─ 초안
```

### 프로젝트 선택

- 접근 가능한 프로젝트만 표시한다.
- 프로젝트 이름, 짧은 설명, 내 확인 필요 건수, 내 수정 필요 건수를 보여준다.
- 프로젝트를 선택하면 개인 받은함이 아닌 공통 공간으로 이동한다.
- 승인 회원 누구나 프로젝트를 생성할 수 있다. 생성자는 해당 프로젝트 관리 담당자가 된다.
- 서비스 관리자 또는 해당 프로젝트 관리 담당자가 승인 회원을 배정한다. 미배정 회원에게는 프로젝트를 노출하지 않으며, 배정된 프로젝트가 없으면 생성·배정 안내를 제공한다.

### 프로젝트 공통 공간

- 전송된 개발 계약과 일반 인수인계를 통합 목록으로 제공한다.
- 목록 항목: 제목, 종류, 송신자, 수신자, 최신 버전, 상태, 최근 변경 시각.
- 개발 계약에는 현재 확정본과 검토 중인 변경안을 구분해 표시한다.
- 담당자, 종류, 상태 필터와 제목 검색을 제공한다.
- ‘내 공간’ 버튼에 내 확인 필요 건수를 표시한다.
- 항목 선택 시 같은 요청 상세 화면으로 이동한다.

### 내 공간

- 받은함: 내 확인 필요, 내 응답 완료, 담당자 변경 필요, 종료. 추가 필수 확인자로 참여한 요청도 포함하며 새 버전은 ‘재검토’ 표시를 붙인다.
- 보낸함: 상대 확인 대기, 내 수정 필요, 처리 완료, 담당자 변경 필요, 종료. 종료 사유는 철회 또는 관리 종료로 구분한다.
- 초안: 미전송 초안과 기존 요청에 대한 미전송 수정안.
- 참조 요청은 ‘참조’ 필터로 구분하고 처리 필요 건수에 포함하지 않는다.
- 공통 공간과 개인 공간은 동일한 데이터를 조회한다. 요청을 복제하지 않는다.

### 개인 상태와 전체 상태

- ‘내 확인 필요’는 최신 전송 버전이 응답 가능한 검토 상태이고, 내가 응답 대상이며, 아직 그 버전에 응답하지 않은 요청만 센다. 참조, 철회, 관리 종료, 수정 요청됨, 담당자 변경 필요는 제외한다.
- 내 동의가 끝났지만 PM이 대기 중이면 ‘내 응답 완료 / 전체: PM 확인 대기’로 표시한다. 내 확인 필요 건수에는 포함하지 않는다.
- 수정 요청된 버전은 모두의 추가 응답을 닫고 송신자의 ‘내 수정 필요’로 이동한다. 수신자 화면에는 ‘전체: 송신자 수정 대기’를 표시하며 이미 남긴 개인 응답은 유지한다.
- ‘내 수정 필요’ 건수는 내가 송신자이고 최신 검토안이 수정 요청된 요청 수이다. 담당자 이탈로 처리가 막힌 요청은 별도 분류한다.
- 새 버전을 전송하면 새 참여자 집합과 새 버전의 응답으로 개인 상태를 다시 계산한다. 개발 계약 송신자는 전송 시 동의 완료이며, 다른 필수 확인자는 재검토 대상이다.

### 요청 상세

- 제목, 종류, 관련 프로젝트, 송신자·수신자, PM 참여 방식.
- 최신 전달 버전, 현재 확정본, 내가 확인한 버전을 구분해 표시한다.
- 본문, 첨부, 관련 PR·커밋 링크, 이전 버전과의 변경 내용.
- 사람별 확인·동의 상태와 시각, 수정 요청 의견, 버전 이력.
- Codex 조회 기록은 사람의 확인 기록과 별도 영역에 표시한다.
- 일반 인수인계 버튼: ‘내용 확인 완료’, ‘수정 요청’.
- 개발 계약 버튼: ‘이 버전에 동의’, ‘수정 요청’.
- 현재 사용자가 처리할 대상이 아니거나 검토가 종료·중단된 상태이면 응답 버튼을 제공하지 않는다. 버튼을 숨기는 것과 별개로 서버에서도 같은 조건을 검증한다.
- 이전 버전 열람 시 과거 기록임을 표시하고 응답 버튼을 비활성화한다.

## 5. 요청 내용과 버전

공통 필수 정보는 제목, 종류, 프로젝트, 송신자, 주 수신자, 본문이다. 첨부 파일과 코드 링크는 선택 사항이다.

Codex 초안 양식은 다음을 제안한다.

| 일반 인수인계 | 개발 계약 |
|---|---|
| 완료한 내용 | 제안하는 계약 내용 |
| 상대가 알아야 할 사항 | 기존 확정본과의 차이 |
| 남은 작업·제약 | 변경 이유와 영향 |
| 관련 PR·커밋 | 관련 PR·커밋·스펙 |

본문은 웹에 저장되는 원본이다. Markdown 파일을 첨부하는 것도 가능하지만 별도 파일 업로드가 필수는 아니다. 긴 원시 에이전트 대화 기록의 자동 수집은 범위에서 제외한다.

전송 시 버전 번호를 부여하고 본문·첨부 참조·참여자 구성을 고정한다. 수정 요청에 답할 때는 같은 요청 아래 새 버전을 추가한다. 자동 변경 비교는 본문 기준으로 제공하며, 첨부는 추가·제거·교체 여부를 표시한다.

## 6. 일반 인수인계 흐름

```text
개인 초안 → 사람 검토·전송 → 확인 대기
                             ├─ 확인 체크 → 확인 완료
                             └─ 수정 요청 → 송신자 수정 → 새 버전 전송 → 재검토 필요
```

수신자가 확인하면 서버가 해당 사용자·요청·버전·시각을 기록하고 송신자에게 자동 회신한다. ‘v2 내용을 확인했습니다’처럼 버전을 명시한다. 이 동작은 후속 작업을 완료했다는 의미가 아니다.

새 버전이 도착하면 기존 확인 기록은 보존하되 최신 버전은 재검토 필요로 표시한다. 반복 클릭과 재시도는 회신을 중복 생성하지 않는다.

## 7. 개발 계약 흐름

```text
개인 초안 → 송신자 명시적 동의·전송 → 검토 대기
                                      ├─ 필수 확인자 모두 동의 → 확정
                                      └─ 수정 요청 → 새 버전 검토
```

- 필수 확인 집합은 송신자와 주 수신자, 필요하면 추가 PM이다.
- 참조 PM의 열람 여부는 확정 조건에 포함하지 않는다.
- 동의는 특정 버전에만 유효하다. 이전 동의를 새 버전에 자동 승계하지 않는다.
- 필수 확인자가 수정 요청하면 해당 검토 버전은 확정할 수 없다. 새 버전을 제출한다.
- 새 변경안이 진행 중이어도 기존 확정본은 유지한다. 첫 계약이 아직 확정되지 않았다면 ‘확정본 없음’으로 표시한다.
- 신규·변경 버전이 확정되면 계약의 현재 유효 버전을 갱신하고 이전 확정본을 이력으로 보존한다. 폐기 확정은 아래 규칙을 따른다.
- 이전 화면을 열어둔 상태에서 새 버전이 발행되면 기존 화면의 동의 처리를 거부하고 새 버전 검토를 안내한다.
- 검토 중인 제안 철회는 기존 확정본을 폐기하지 않는다. 확정된 계약의 폐기는 별도 변경 제안과 합의로 처리한다.

### 계약 식별과 폐기

- 계약은 요청과 별도의 고유 ID를 가진다. 동일 계약의 신규·변경·폐기 제안을 해당 ID에 연결한다. 담당자 복구로 새 요청을 만들더라도 계약 ID는 유지한다.
- 계약별로 진행 중인 검토안은 하나만 허용한다. 새 버전은 기존 검토 버전을 대체하며, 종료된 요청 대신 연결된 새 요청을 만들 때도 이 조건을 지킨다.
- 변경·폐기 제안은 검토 기준이 된 확정본 ID를 기록한다. 확정 시 기준 확정본이 여전히 유효한지 서버에서 확인하고, 달라졌다면 확정을 거부하고 재검토를 요구한다.
- 폐기 제안에는 폐기 이유와 대상 확정본을 명시하며 신규·변경과 같은 필수 동의 규칙을 적용한다.
- 폐기 검토 중에는 기존 확정본이 유효하다. 폐기가 확정되면 계약은 ‘폐기됨’이 되고 현재 유효 버전은 없어진다. 마지막 확정본과 폐기 합의 기록은 보존한다.
- 웹과 Codex의 ‘현재 유효 계약’ 목록은 폐기된 계약을 제외한다. 계약 ID를 직접 조회하면 폐기 상태·폐기 시각·이력을 반환하고 과거 본문을 현행 계약으로 표시하지 않는다.
- 폐기된 계약은 첫 버전에서 재활성화하지 않는다. 다시 필요하면 이전 계약 링크를 포함한 신규 계약으로 제안한다.

### 상태 전환표

아래 상태는 전송된 검토 버전의 상태다. 일반 인수인계의 ‘확인 대기’와 개발 계약의 ‘검토 대기’는 서버에서 모두 응답 가능한 검토 상태로 취급한다.

| 현재 상태 | 명령·조건 | 결과 |
|---|---|---|
| 검토 대기 | 미응답 수신자의 일반 인수인계 확인 | 확인 완료, 송신자 자동 회신 |
| 검토 대기 | 미응답 필수 확인자의 계약 동의 | 응답 저장, 전원 동의 시 확정 |
| 검토 대기 | 미응답 응답 대상자의 수정 요청 | 수정 요청됨, 모든 추가 응답 차단, 송신자에게 의견 회신 |
| 검토 대기 / 수정 요청됨 | 송신자의 새 버전 전송 | 이전 버전은 대체됨, 새 버전은 검토 대기 |
| 검토 대기 / 수정 요청됨 | 송신자의 사유 포함 철회 | 철회, 추가 응답·해당 요청 재전송 차단 |
| 검토 대기 / 수정 요청됨 | 필수 담당자 접근 권한 상실 | 담당자 변경 필요, 응답·재전송 중단 |
| 담당자 변경 필요 | 권한 있는 관리자의 사유 포함 종료 | 관리 종료, 필요하면 새 연결 요청 생성 |
| 확인 완료 / 확정 | 송신자의 새 내용 제안 | 기존 버전의 응답은 보존, 별도 새 버전 검토 시작; 계약 유효성은 새 합의까지 유지 |
| 수정 요청됨 / 대체됨 / 철회 / 관리 종료 / 확인 완료 / 확정 | 기존 버전에 대한 새 확인·동의·수정 요청 | 거부, 현재 상태 안내 |

각 사용자는 한 버전에 한 번만 응답한다. 같은 응답의 재시도는 기존 결과를 돌려주며, 이미 제출한 동의를 수정 요청으로 바꾸는 등 응답 변경은 허용하지 않는다. 동의 후 변경이 필요하면 송신자에게 새 버전 제안을 요청하고 그 버전을 다시 검토한다. 철회·관리 종료된 요청은 새 연결 요청으로만 이어간다.

서버는 명령마다 권한, 요청·버전 상태, 최신 버전, 기존 응답, 계약 기준 확정본을 함께 검증하고 상태 변경을 원자적으로 저장한다. 철회와 마지막 동의가 동시에 들어오면 먼저 저장된 유효 명령만 성공한다. 철회가 먼저면 동의를 거부하고, 확정이 먼저면 철회를 거부한다. 수정 요청과 다른 담당자의 동의가 겹쳐도 수정 요청이 저장된 버전은 확정되지 않는다.

## 8. PM 참여

송신자가 전송 전 PM을 필수 확인 또는 참조로 지정한다. 주 수신자는 수정 요청 의견을 통해 PM 추가 검토를 요청할 수 있다. 참여자 변경을 포함한 새 버전을 송신자가 전송한다.

필수 PM은 별도의 응답 관계를 가지되 원래 요청과 버전을 공유한다. 따라서 사용자 관점에서 주 담당자 간 1:1 인계 흐름은 유지되고, 공통 화면에서 모든 필수 확인 상태를 볼 수 있다.

일반 인수인계의 PM 참여는 첫 버전에서 참조로 제한한다. 추가 승인이 필요하면 개발 계약 유형을 사용한다.

## 9. Codex와 디스코드 연동 경계

이 절은 목표 인터페이스를 정의한다. 현재 설치된 Codex의 지원 방식, 인증 및 디스코드 설치 권한은 구현 전 기술 검증이 필요하며 지원이 확인된 것으로 간주하지 않는다.

### Codex

- 사용자를 식별한 연결을 통해 프로젝트 목록과 접근 권한을 확인한다.
- 초안 생성·갱신, 자신의 받은 요청 조회, 특정 버전 조회, 현재 유효 계약 조회를 목표 기능으로 한다. 폐기 상태를 포함한 특정 계약의 이력 조회는 유효 계약 목록과 구분한다.
- 초안 저장 후 웹 검토 링크를 반환한다. 최종 전송·동의는 웹에서 사람이 수행한다.
- 에이전트 연동에는 사람의 동의나 최종 전송을 대행할 권한을 주지 않는다.
- 조회 기록은 명시적으로 해당 버전 본문을 가져간 사실만 뜻한다. 에이전트가 이해했거나 코드에 반영했다고 표시하지 않는다.
- 모든 Codex 활동 자동 감지, 종료된 에이전트 자동 실행, 코드의 계약 준수 자동 판정은 첫 버전에서 제외한다.

### 디스코드

- 프로젝트별 지정 채널에 요청 도착·회신·새 버전·계약 확정 알림과 웹 링크를 게시하는 구성을 기본 제안으로 한다.
- 웹에서 지정한 담당자와 연결된 디스코드 계정을 멘션한다. 팀원 본인이 계정 연결을 확인한다.
- 알림에는 제목·대상·상태·버전만 포함하고 본문과 첨부 열람은 인증된 웹에서 제공한다.
- 확인·동의·수정 요청 버튼은 첫 버전에서는 웹에 둔다.
- 디스코드에 수동으로 쓴 메시지를 자동으로 계약 승인으로 해석하지 않는다.
- 디스코드 알림 실패가 웹 요청 저장·회신을 취소하지 않는다. 웹에 발송 상태를 표시하고 재시도한다.

## 10. 확정 기술과 운영 구조

React·TypeScript 프론트엔드, Node.js·NestJS·TypeScript 백엔드(기본 Express 어댑터), PostgreSQL·Prisma로 구성한다. 운영은 GCP 서울 리전 asia-northeast3의 VM 한 대와 Docker Compose를 사용한다. 패키지 버전과 실제 명령은 구현 시 검증·고정한다.

```text
웹 브라우저 ──────────┐
                     ├─ 서비스 API ─ 데이터베이스
사용자별 Codex 연결 ──┘       │       첨부 저장소
                             └─ 알림 작업 처리 ─ 디스코드
```

- 요청·버전·응답·이력은 서비스 데이터베이스가 원본이다.
- 첨부는 접근 권한을 확인한 후 내려받으며 프로젝트 코드 저장소에 저장하지 않는다.
- 상태 변경과 알림 발송 요청을 함께 기록하고, 알림은 별도 처리해 실패 시 재시도한다.
- 웹 화면은 저장 성공 직후 상태를 반영한다. 다른 사용자의 화면은 주기적 갱신으로 시작할 수 있다.
- 내부 사용부터 팀·프로젝트 구분을 모든 데이터 접근에 적용해 공개 서비스 확장의 기반을 마련한다.
- 개발 환경에서는 PostgreSQL만 Docker로 실행하고 React·NestJS는 로컬 실행한다. 운영 환경에서는 웹 서버·NestJS·PostgreSQL을 Compose로 구성한다.
- PostgreSQL은 직접 운영하며 DB 데이터·첨부 원본은 VM 영구 디스크에 보관한다. 컨테이너 교체 시 데이터가 사라지지 않도록 연결한다.
- DB와 첨부는 하루 1회 Cloud Storage에 정합성을 갖춘 세트로 백업하고 7일 보관한다. 운영 전 별도 환경에서 복구를 검증한다. 원본 첨부 저장소와 백업 저장소는 구분한다.
- 비용 최소화를 우선하고 신규 무료 크레딧을 활용한다. 실제 자격·잔액·만료와 이후 비용을 배포 전에 확인하며 서울 VM이 계속 무료라고 가정하지 않는다.

| 에이전트 조회 | 사용자, 요청 버전, 조회 시각 |
| 알림 | 대상 이벤트, 발송 상태, 재시도·중복 방지 키 |
| 전송 시도 | 사용자·프로젝트별 고유 키, 초안 리비전, 입력 요약값, 저장된 요청·버전·결과 |

전체 검토 상태는 최신 전송 버전의 상태·응답과 종료·이탈 이력에서 결정한다. 개인 상태는 해당 사용자의 역할·응답·처리 가능 여부에서 별도로 계산한다. 계약의 유효 상태는 마지막으로 확정된 합의에서 관리하며 미완료 검토안의 상태로 덮어쓰지 않는다.

## 12. 오류와 동시 처리

- 중복 체크: 동일 사용자·버전의 같은 응답은 한 번만 저장하고 자동 회신도 한 번만 발생한다.
- 버전 충돌: 화면의 버전과 서버 최신 버전이 다르면 응답을 저장하지 않고 갱신을 안내한다.
- 동시 동의: 모든 필수 확인이 모이는 순간 확정 처리를 한 번만 수행한다.
- 같은 버전의 경합: 7장의 전환표에 따라 철회·동의·수정 요청·새 버전 발행을 순서가 있는 원자적 변경으로 처리한다. 종료된 상태를 다시 열지 않는다.
- 전송 재시도: 최초 클릭 때 전송 키와 초안 리비전을 고정하고, 결과가 불명확하면 같은 키로 조회·재시도한다. 동일 키·동일 입력이면 이미 저장된 요청·버전·결과를 반환한다. 같은 키에 다른 입력을 보내면 충돌로 거부한다.
- 중복 생성 방지: 동일 초안 리비전은 한 번만 발행한다. 다른 탭에서 다른 키로 재전송해도 같은 발행 결과를 반환한다. 의도적인 새 전송은 새 초안 리비전과 새 전송 키를 사용한다.
- 전송 결과 유실: 저장 성공 여부를 모르면 ‘전송 결과 확인 중’으로 표시하고 입력을 고정한다. 저장 실패가 확인된 경우에만 초안 편집·재전송을 허용한다. 저장되지 않은 내용을 전송 완료로 표시하지 않는다.
- 요청·버전 저장과 알림 이벤트 생성은 함께 확정한다. 동일 전송은 알림 이벤트를 하나만 만든다. 외부 디스코드가 메시지를 수신한 뒤 응답을 유실하는 경우에는 실제 게시 중복 가능성을 구분해 기록하고, 외부 전달까지 정확히 한 번을 보장한다고 표시하지 않는다.
- 첨부 실패: 업로드 완료 전 전송을 막고 실패한 첨부를 다시 올리거나 제거할 수 있게 한다.
- 알림 실패: 요청과 회신은 유지하고 알림만 재시도한다. 웹 받은함은 정상적으로 조회된다.
- 접근 권한 상실: 해당 사용자의 조회·다운로드·응답을 차단하고 기존 이력을 보존한다. 미완료 요청은 3장의 담당자 이탈 복구 절차를 적용한다.
- 에이전트 미접속: 마지막 조회 기록만 보여주며 읽음·진행 상태를 추정하지 않는다.

## 13. 첫 버전 범위와 제외 사항

포함: Google·Discord 가입·승인·계정 연결, 최초 서비스 관리자와 관리자 권한 부여, 승인 회원의 프로젝트 생성, 프로젝트별 멤버 배정, 공통 공간, 개인 받은함·보낸함·초안, 요청 본문과 첨부, 버전과 변경 비교, 확인·동의·수정 요청, 선택적 PM, 자동 회신, 디스코드 알림, Codex 연결 검증 및 검증된 방식의 연동, VM 운영·백업·복구 검증.

제외: 관리자 승인 없는 자동 가입, 공개 서비스용 셀프서비스 조직 생성, 결제, 요금제, 자동 담당자 추천, 복잡한 승인 단계 편집기, 일반 채팅, 전체 개발 업무 관리, 코드 계약 준수 검사, 에이전트 자동 실행, 다른 AI 도구 연동, 무제한 파일 미리보기.

기존 코드 저장소의 문서 삭제·이동이나 기존 디스코드 이력 전체 가져오기는 별도 작업이다.

## 14. 검증 기준

1. 승인된 사용자가 로그인 후 배정된 프로젝트를 선택하면 해당 공통 공간이 먼저 열린다. 미승인 사용자는 대기 화면만 본다.
2. 공통 공간에서 다른 팀원 간 전송된 요청의 본문과 첨부를 열람할 수 있다.
3. 같은 프로젝트 팀원이어도 남의 초안이나 남의 응답 버튼에는 접근할 수 없다.
4. 수신자가 확인하면 송신자 보낸함 상태가 갱신되고 회신 알림이 생성된다.
5. 수정 요청 의견이 원래 송신자에게 전달되고 재전송은 같은 요청의 새 버전이 된다.
6. 새 버전은 이전 확인을 승계하지 않고 재검토 대상으로 표시된다.
7. 개발 계약에서 필수 PM의 동의는 확정 조건이며 참조 PM의 열람은 조건이 아니다.
8. 새 변경안 검토·수정·철회가 기존 확정본을 바꾸지 않는다.
9. 오래된 화면에서 체크하거나 중복 클릭해도 잘못된 확정·중복 회신이 생기지 않는다.
10. 디스코드 장애 중에도 웹에서 요청을 생성하고 처리할 수 있다.
11. 다른 팀·프로젝트의 API와 첨부 접근을 차단한다.
12. Codex 조회는 사람의 승인으로 처리되지 않고, 연동 자격으로 승인 API를 호출할 수 없다.
13. 철회와 마지막 동의를 동시에 시도하면 하나만 성공한다. 철회된 버전은 확정되지 않고, 확정된 버전은 철회되지 않는다.
14. 수정 요청·확정·철회·관리 종료된 버전에는 새로운 응답을 저장하지 않는다. 동일 응답 재시도는 기존 결과만 반환하며 동의에서 수정 요청으로 바꾸는 호출은 거부한다.
15. 송신자·수신자·필수 PM이 접근 권한을 잃으면 미완료 요청은 담당자 변경 필요가 된다. 관리 종료와 연결 요청 생성 후에도 이전 확인을 승계하지 않고 기존 확정 계약을 유지한다. 참조자 이탈은 검토를 막지 않는다.
16. 폐기 검토 중에는 기존 계약이 유효하며, 폐기 확정 후 웹·Codex의 유효 계약 목록에서는 제외된다. 직접 조회에서는 폐기 상태와 과거 기록을 구분해 보여준다.
17. 서버 저장 직후 응답 유실을 재현하고 동일 전송을 재시도하면 요청·버전·알림 이벤트 수가 늘지 않는다. 다른 탭의 동일 초안 리비전 전송도 중복 발행되지 않는다.
18. 수신자 동의 후 필수 PM만 대기하면 수신자의 확인 필요 건수는 0이고 전체 상태는 PM 확인 대기이다. 새 버전 전송 후에는 수신자의 재검토 필요 건수가 다시 증가한다.
19. 같은 계약의 경쟁 변경안과 오래된 기준 확정본으로 합의를 시도하면 차단된다. 관리 종료 후 새 담당자의 연결 요청도 같은 계약 ID와 유효성 규칙을 유지한다.
20. Google·Discord 신규 가입자는 승인 전 프로젝트 조회·생성·첨부 다운로드 API를 사용할 수 없다. 서비스 관리자 승인 후에도 배정되지 않은 프로젝트에는 접근하지 못한다.
21. 승인 회원이 프로젝트를 생성하면 해당 프로젝트의 멤버·관리 담당자가 된다. 다른 프로젝트의 권한은 얻지 않는다.
22. 프로젝트 관리 담당자는 승인 회원만 자기 프로젝트에 추가·제외할 수 있다. 다른 프로젝트 멤버 변경·가입 승인·서비스 관리자 권한 부여 시도는 차단된다.
23. 명시적으로 지정된 최초 관리자만 초기 관리자 권한을 받고, 서비스 관리자만 다른 승인 회원에게 그 권한을 부여한다. 관리자도 미배정 프로젝트의 본문과 남의 초안을 조회할 수 없다.
24. 로그인 상태에서 다른 제공자를 연결하면 두 로그인 수단이 같은 승인 상태·프로젝트·받은함을 사용한다. 이메일 일치에 따른 자동 병합이나 다른 회원의 제공자 계정 덮어쓰기는 발생하지 않는다.
25. 컨테이너를 교체해도 DB·첨부 데이터가 남으며, 하루 1회 외부 백업과 7일 보관 정책을 적용한다. 별도 환경에서 DB·첨부를 복구해 참조 정합성과 권한 있는 다운로드를 확인한다.

권한·버전별 합의·중복 처리·알림 재시도는 자동 검증하고, 프로젝트 선택부터 양방향 회신까지는 실제 두 사용자 계정과 시험 디스코드 채널로 통합 검증한다.

## 15. 내부 시험 운영과 공개 전 확장

4~5명 팀의 한 프로젝트에서 시작한다. 수동 복사·전달 과정과 비교해 다음을 관찰한다.

- 확인 여부를 디스코드에서 다시 묻는 횟수.
- 오래된 계약을 참조해서 재설명·재작업한 사례.
- 요청 도착부터 첫 응답까지 걸린 시간.
- 수정 요청 후 새 버전 전달이 누락된 사례.
- 초안 검토·전송에 드는 수고와 웹 접근의 편의성.

관측 수치는 제품 개선에 사용하며 개인 평가나 성과 점수로 사용하지 않는다. 목표 수치는 초기 사용 기록을 본 뒤 정한다.

초기 운영 전부터 백업·복구를 검증한다. 공개 전에는 팀 간 격리 검증을 확대하고 공개 가입·조직 관리, 탈퇴와 데이터 내보내기·삭제, 서비스 운영 및 과금 여부를 별도 설계한다. 첨부 용량 등 미확정 조건은 기술 결정 문서에서 추적한다.

## 16. 다음 단계

확정된 스택과 정책을 기준으로 구현 계획을 작성한다. 세부 버전·세션 관리·Codex 연결 방식·디스코드 설정과 실제 배포 값은 기술 결정 문서의 미결정 목록에서 확인한다. 이 명세는 제품을 구현하거나 외부에 배포했다는 의미가 아니다.
