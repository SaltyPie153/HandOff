# Feature Specification: 소셜 로그인과 가입 승인

**Feature Branch**: feature/auth-onboarding
**Created**: 2026-09-25
**Status**: Draft — 사용자 검토 전
**Input**: 다른 PC에서 앱 기본 골격을 진행하는 동안 로그인·가입 승인 기능의 SDD 명세를 준비한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 로그인 후 승인 대기 (Priority: P1)

팀원은 Google 또는 Discord로 로그인한다. 신규 계정은 승인 대기 화면을 보고, 승인 전에는 업무 자료에 접근하지 못한다.

**Why this priority**: 사용자 식별과 가입 승인 경계가 있어야 이후 기능을 안전하게 연다.
**Independent Test**: 두 제공자의 새 계정과 재방문 계정으로 로그인·접근 제한을 확인한다.

**Acceptance Scenarios**:

1. **Given** 연결되지 않은 제공자 계정, **When** 로그인에 성공하면, **Then** 승인 대기 회원 한 명이 생성되고 대기 화면이 나타난다. (FR-001, FR-002)
2. **Given** 이미 등록된 제공자 계정, **When** 다시 로그인하면, **Then** 기존 회원과 현재 승인 상태를 사용한다. (FR-002)
3. **Given** 승인 대기 회원, **When** 프로젝트 조회·생성, 본문·첨부 열람, 업무 변경을 시도하면, **Then** 서버가 거부한다. (FR-003)
4. **Given** 비로그인 방문자 또는 로그아웃한 회원, **When** 회원 전용 기능에 접근하면, **Then** 자료를 보여주지 않는다. (FR-004)
5. **Given** 제공자 인증이 실패하거나 취소된 방문자, **When** 로그인 결과를 확인하면, **Then** 실패를 안내하고 로그인 상태를 만들거나 비밀값을 노출하지 않는다. (FR-001, FR-013)

### User Story 2 - 서비스 관리자가 가입 승인 (Priority: P1)

서비스 관리자는 대기 회원을 확인해 가입을 승인한다. 승인된 회원도 기존 프로젝트는 별도로 배정받아야 접근할 수 있다.

**Why this priority**: 소셜 로그인 자체가 내부 업무 접근 권한이 되어서는 안 된다.
**Independent Test**: 관리자·일반 회원·대기 회원으로 승인, 무단 승인, 승인 직후 접근을 확인한다.

**Acceptance Scenarios**:

1. **Given** 대기 회원, **When** 서비스 관리자가 승인하면, **Then** 대상·처리자·시각을 기록하고 새 요청부터 승인 상태를 적용한다. (FR-005, FR-006)
2. **Given** 일반 또는 대기 회원, **When** 대기 목록 조회·가입 승인·관리자 권한 부여를 시도하면, **Then** 서버가 거부한다. (FR-005, FR-008)
3. **Given** 서비스 최초 기동, **When** 임의의 회원이 먼저 로그인하면, **Then** 관리자가 되지 않는다. 명시 지정된 실제 회원만 최초 관리자가 된다. (FR-007)
4. **Given** 프로젝트에 미배정된 승인 회원 또는 관리자, **When** 기존 프로젝트 자료를 요청하면, **Then** 접근이 거부된다. (FR-009)
5. **Given** 승인 회원, **When** 서비스 관리자가 그 회원에게 관리자 권한을 부여하면, **Then** 대상·처리자·시각이 기록되고 일반 회원은 같은 변경을 할 수 없다. (FR-008)

### User Story 3 - 두 로그인 수단 연결 (Priority: P2)

회원은 로그인한 상태에서 다른 제공자로 직접 인증해 같은 내부 회원에 연결한다.

**Why this priority**: 로그인 수단 변경으로 받은함이 분리되거나 다른 사람의 자료가 합쳐지지 않게 한다.
**Independent Test**: 양방향 연결, 같은 이메일의 별도 계정, 타인에게 연결된 계정 충돌을 확인한다.

**Acceptance Scenarios**:

1. **Given** Google 또는 Discord로 로그인한 회원, **When** 다른 제공자 인증을 완료해 연결하면, **Then** 두 수단이 같은 내부 회원과 승인 상태를 사용한다. (FR-010)
2. **Given** 이메일이 같은 별도 계정, **When** 단순 로그인하면, **Then** 자동 병합하지 않는다. (FR-011)
3. **Given** 다른 회원에게 이미 연결된 제공자 계정, **When** 연결을 시도하면, **Then** 거부하고 두 회원의 자료와 연결을 보존한다. (FR-012)
4. **Given** 연결 인증이 취소·실패한 상황, **When** 원래 회원으로 돌아오면, **Then** 기존 연결과 승인 상태가 유지된다. (FR-012)

### Edge Cases

- 동일한 제공자 계정의 첫 로그인이 동시에 일어나도 회원은 하나만 생성한다.
- 승인 직전 열린 오래된 화면이나 세션은 다음 요청의 현재 권한 검사에 우선하지 않는다.
- 이메일이 없거나 다른 계정과 중복되어도 검증된 제공자 계정 식별자로 구분한다.
- 연결 도중 세션이 만료되거나 다른 회원이 먼저 연결하면 안전하게 실패한다.
- 제공자 장애·인증 취소는 로그인·연결 성공으로 표시하지 않는다.
- 관리자는 프로젝트 미배정 상태에서 그 프로젝트의 본문·첨부·타인의 초안을 볼 수 없다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Google와 Discord 인증을 제공하고, 제공자 인증이 완료되지 않으면 로그인으로 처리하지 않아야 한다.
- **FR-002**: 신규 제공자 계정으로 승인 대기 회원을 한 번만 생성하며 재로그인은 같은 내부 회원과 상태를 사용해야 한다.
- **FR-003**: 대기 회원은 자신의 대기 상태 확인·로그아웃·본인이 인증한 다른 제공자 연결만 이용하며 프로젝트·인수인계·계약·첨부 접근과 업무 변경은 서버에서 차단해야 한다.
- **FR-004**: 비로그인 및 로그아웃 상태의 회원 전용 접근을 차단해야 한다.
- **FR-005**: 서비스 관리자만 대기 목록을 조회하고 가입을 승인할 수 있어야 한다. 목록에는 승인 판단에 필요한 최소 식별 정보만 보여야 한다.
- **FR-006**: 승인은 대상·처리자·시각을 기록하고 중복 요청에도 한 번만 유효하게 적용해야 한다. 권한은 새 요청마다 현재 저장된 상태로 판단해야 한다.
- **FR-007**: 실제 최초 관리자는 명시 지정으로만 부여하고 첫 가입자·첫 로그인자의 자동 승격을 금지해야 한다.
- **FR-008**: 서비스 관리자만 이미 승인된 회원에게 서비스 관리자 권한을 부여할 수 있어야 하며 대상·처리자·시각을 기록해야 한다.
- **FR-009**: 승인 회원의 프로젝트 생성 자격과 기존 프로젝트 배정·접근은 구분해야 한다. 관리자 역할만으로 콘텐츠 접근을 허용하지 않아야 한다.
- **FR-010**: 로그인한 회원이 다른 제공자의 인증을 직접 완료한 경우에만 그 제공자 계정을 자신의 내부 회원에 연결해야 한다.
- **FR-011**: 이메일 또는 표시 이름 일치로 회원을 자동 병합하지 않아야 한다.
- **FR-012**: 타인에게 연결된 제공자 계정을 덮어쓰거나 자동 병합하지 않아야 한다. 연결 실패·취소·충돌 시 기존 상태를 보존해야 한다.
- **FR-013**: 실패 사유를 사용자가 구분할 수 있게 안내하되 인증 비밀값과 다른 회원의 보호된 자료를 노출하지 않아야 한다.

### Key Entities *(include if feature involves data)*

- **회원**: 내부 식별자, 승인 상태, 서비스 관리자 여부.
- **제공자 계정 연결**: 검증된 Google 또는 Discord 계정 식별자와 해당 내부 회원. 제공자 계정 하나는 회원 하나에만 속한다.
- **가입 승인 기록**: 대상, 처리한 관리자, 처리 시각.
- **관리자 권한 부여 기록**: 대상, 처리한 관리자, 처리 시각.
- **로그인 세션**: 현재 로그인한 내부 회원을 식별하고 로그아웃 시 무효화할 수 있는 이용 상태.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Google·Discord 각 제공자의 첫 로그인과 재로그인 검증에서 같은 제공자 계정의 회원 중복 생성 0건.
- **SC-002**: 대기 회원의 프로젝트 조회·생성, 본문·첨부 접근, 업무 변경 검증에서 허용 0건.
- **SC-003**: 관리자 승인 후 새 요청에 승인 상태가 반영되고 일반 회원의 승인·관리자 부여 허용 0건.
- **SC-004**: 첫 로그인자의 자동 관리자 승격과 미배정 관리자의 콘텐츠 열람 0건.
- **SC-005**: 두 방향의 계정 연결, 이메일 중복, 연결 충돌, 인증 취소 검증에서 잘못된 회원 병합·연결 변경 0건.
- **SC-006**: 내부 팀원 4~5명이 자신의 로그인·승인 상태를 구분하고 관리자는 추가 구두 안내 없이 대기 회원을 찾아 승인할 수 있다.

## Assumptions

- 이 명세는 제품 원본의 R20·R23·R24와 기술 설계의 회원 정책을 구체화한다.
- 프로젝트 생성·배정·콘텐츠는 후속 기능이다. 이번 기능은 접근 경계를 제공하고 검증한다.
- 최초 관리자에게 사용할 실제 계정 식별값과 운영 절차는 배포 전 확정한다. 미지정 상태에 자동 관리자 우회 경로는 없다.
- 가입 거절, 비활성화·재가입, 계정 연결 해제, 프로젝트 관리자 양도는 범위 밖이다.
- Discord 로그인과 Discord 알림 채널 설정은 별개다. 로그인에 알림 연결을 요구하지 않는다.
- 세션 관리 방식, 외부 제공자 설정값과 화면 경로는 계획 단계에서 결정한다.
- 앱 기본 골격 통합 전에는 이 브랜치에서 문서만 작성하고 공용 코드·의존성을 수정하지 않는다.
