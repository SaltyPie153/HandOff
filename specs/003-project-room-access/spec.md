# Feature Specification: 프로젝트 룸과 멤버 권한

**Feature Branch**: `feature/project-room-access`

**Created**: 2026-09-28

**Status**: Approved for planning (2026-09-28)

**Input**: 승인 회원의 프로젝트 생성·멤버 배정·프로젝트별 접근 권한을 먼저 만들고, 팀원에게 공개되는 인수인계·계약 목록은 다음 기능으로 분리한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 승인 회원이 프로젝트를 만들고 입장한다 (Priority: P1)

승인된 회원은 프로젝트 이름과 짧은 설명을 입력해 새 프로젝트를 만들고, 자신의 프로젝트 선택 화면에서 그 룸에 들어간다. 생성과 동시에 해당 프로젝트의 멤버이자 관리 담당자가 된다.

**Why this priority**: 팀이 공유할 공간과 그 공간을 관리할 책임자를 함께 만들어야 이후 인수인계가 배정된 팀 안에서 시작된다.

**Independent Test**: 승인 회원 한 명으로 프로젝트를 만들고 선택 화면·빈 룸·관리 권한을 확인한다. 승인 대기 회원으로 같은 동작을 시도해 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 승인 회원에게 배정된 프로젝트가 없을 때, **When** 유효한 이름으로 프로젝트를 만들면, **Then** 새 프로젝트가 한 번 생성되고 그 회원이 멤버·관리 담당자로 등록되며 자신의 선택 목록에 표시된다.
2. **Given** 생성자가 새 프로젝트를 선택했을 때, **When** 룸에 들어가면, **Then** 프로젝트명과 멤버 현황 및 아직 공유된 요청이 없다는 안내를 본다.
3. **Given** 승인 대기 또는 로그인하지 않은 사용자일 때, **When** 프로젝트 생성이나 룸 입장을 시도하면, **Then** 생성·열람이 거부된다.

---

### User Story 2 - 권한 있는 관리자가 승인 회원을 배정한다 (Priority: P1)

프로젝트 관리 담당자는 자기 프로젝트에 승인 회원을 추가하거나 일반 멤버를 제외한다. 서비스 관리자는 프로젝트 배정을 관리할 수 있지만, 배정받지 않은 프로젝트의 룸 콘텐츠를 볼 수 없다.

**Why this priority**: 같은 팀의 작업자만 공유 룸을 사용할 수 있게 하고, 서비스 가입 승인과 프로젝트 멤버십을 분리한다.

**Independent Test**: 프로젝트 두 개와 승인 회원 두 명으로 추가·중복 추가·제외를 수행하고, 자기 프로젝트 관리자·다른 프로젝트 관리자·서비스 관리자·일반 회원의 결과를 비교한다.

**Acceptance Scenarios**:

1. **Given** 자기 프로젝트 관리 담당자와 승인된 비멤버가 있을 때, **When** 관리 담당자가 그 회원을 추가하면, **Then** 멤버 목록과 해당 회원의 프로젝트 선택 목록에 프로젝트가 한 번만 나타난다.
2. **Given** 서비스 관리자가 프로젝트 멤버를 관리할 때, **When** 자신은 그 프로젝트의 멤버가 아니면, **Then** 승인 회원을 추가·제외할 수 있지만 룸 콘텐츠 접근은 거부된다.
3. **Given** 프로젝트 관리 담당자가 일반 멤버를 제외할 때, **When** 변경이 완료되면, **Then** 제외된 회원의 이후 프로젝트 조회·입장 요청은 거부되고 기존 활동 이력은 보존된다.
4. **Given** 승인 대기 회원 또는 다른 프로젝트 관리 담당자일 때, **When** 멤버 추가·제외를 시도하면, **Then** 변경은 거부되고 기존 멤버십은 유지된다.
5. **Given** 권한 있는 관리자가 멤버를 추가·제외했을 때, **When** 변경 기록을 확인하면, **Then** 대상 회원·수행자·시각·변경 종류를 확인할 수 있다.

---

### User Story 3 - 회원은 배정된 프로젝트만 찾고 들어간다 (Priority: P1)

승인 회원의 프로젝트 선택 화면에는 자신이 속한 프로젝트만 표시된다. 프로젝트 ID나 주소를 알아도 다른 프로젝트의 룸과 멤버 현황을 볼 수 없다.

**Why this priority**: 향후 팀 전체에 공개할 인수인계와 계약의 접근 경계를 먼저 확정한다.

**Independent Test**: 프로젝트별로 멤버를 다르게 배정한 뒤 선택 목록과 직접 주소 접근을 비교한다.

**Acceptance Scenarios**:

1. **Given** 회원이 A 프로젝트에만 배정됐을 때, **When** 프로젝트 선택 화면을 열면, **Then** A만 보이고 B는 노출되지 않는다.
2. **Given** 같은 회원이 B 프로젝트의 주소나 식별자를 직접 사용할 때, **When** B의 룸이나 멤버 현황을 요청하면, **Then** 접근이 거부되고 B의 정보가 반환되지 않는다.
3. **Given** 승인 회원에게 배정된 프로젝트가 없을 때, **When** 선택 화면을 열면, **Then** 빈 목록과 프로젝트 생성·배정 안내가 표시된다.

---

### User Story 4 - 계정 연결과 멤버십 변경이 현재 권한에 반영된다 (Priority: P2)

한 회원에게 연결된 Google·Discord 로그인은 동일한 프로젝트 배정을 사용한다. 멤버 제외 등 권한 변경은 이미 열린 화면이나 세션에도 다음 요청부터 반영된다.

**Why this priority**: 로그인 수단이나 오래된 화면을 통해 프로젝트 권한 경계를 우회하지 못하게 한다.

**Independent Test**: 두 제공자에 연결된 한 회원을 프로젝트에 배정하고 각 수단으로 로그인해 같은 목록을 확인한 뒤, 멤버를 제외하고 오래된 화면에서 다시 요청한다.

**Acceptance Scenarios**:

1. **Given** 두 로그인 수단이 한 회원에 연결됐을 때, **When** 각 수단으로 로그인하면, **Then** 같은 프로젝트 목록과 멤버 권한을 얻는다.
2. **Given** 회원이 룸을 열어둔 상태에서 멤버십을 잃었을 때, **When** 화면을 새로고침하거나 다음 요청을 보내면, **Then** 룸 접근이 거부되고 더 이상 선택 목록에 나타나지 않는다.

### Edge Cases

- 같은 회원을 반복해서 추가해도 중복 멤버십이나 중복 관리 권한이 생기지 않는다.
- 가입 승인이 취소되거나 현재 승인 상태가 유효하지 않으면 과거 배정만으로 프로젝트에 접근하지 못한다. 가입 상태 변경 자체는 이 기능의 범위 밖이다.
- 다른 프로젝트의 식별자를 넣거나 오래된 화면에서 멤버 변경을 재시도해도 권한 판단은 현재 상태를 따른다.
- 관리 담당자의 제외·양도와 마지막 관리 담당자 제거는 이번 범위에서 허용하지 않는다. 별도 정책을 정할 때까지 프로젝트를 관리자 없는 상태로 만들지 않는다.
- 멤버 제외 후 미완료 인수인계 담당자 처리와 기존 계약 이력은 후속 요청 기능에서 원본 명세의 ‘담당자 변경 필요’ 규칙을 적용한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 현재 승인된 회원만 프로젝트를 생성하게 해야 한다.
- **FR-002**: 프로젝트 생성은 프로젝트와 생성자의 멤버십·관리 담당자 권한을 함께 확정해야 하며, 일부만 만들어진 상태를 남기지 않아야 한다.
- **FR-003**: 승인 회원의 프로젝트 선택 목록은 현재 배정된 프로젝트만 표시해야 한다. 배정이 없으면 생성·배정 안내를 제공해야 한다.
- **FR-004**: 프로젝트 룸과 룸 안의 멤버 현황은 현재 승인된 해당 프로젝트 멤버에게만 공개해야 한다.
- **FR-005**: 프로젝트 관리 담당자는 자기 프로젝트에만 승인 회원을 추가하고 일반 멤버를 제외할 수 있어야 한다.
- **FR-006**: 서비스 관리자는 별도 배정 관리 화면에서 프로젝트의 기본 정보·멤버 현황을 보고 승인 회원의 배정을 관리할 수 있어야 한다. 서비스 관리자 권한만으로 미배정 프로젝트의 룸 콘텐츠를 열람할 수 없어야 한다.
- **FR-007**: 승인 대기 회원의 프로젝트 생성, 일반 회원과 타 프로젝트 관리 담당자의 무권한 멤버 변경, 미배정 회원의 룸 열람은 화면 경로와 직접 요청 모두에서 거부해야 한다.
- **FR-008**: 멤버 추가를 반복해도 같은 회원과 프로젝트 사이의 유효 멤버십은 하나여야 한다.
- **FR-009**: 멤버십 변경은 이후 요청의 접근 판단과 프로젝트 선택 목록에 반영되어야 하며, 과거 활동 이력을 삭제하지 않아야 한다.
- **FR-010**: 한 내부 회원에게 연결된 여러 로그인 수단은 같은 프로젝트 멤버십을 사용해야 한다.
- **FR-011**: 프로젝트 멤버 추가·제외 기록에는 대상, 변경을 수행한 회원, 시각, 변경 종류를 남겨야 한다.
- **FR-012**: 이번 기능의 룸은 프로젝트 정보와 멤버 현황 및 빈 요청 상태를 제공해야 한다. 인수인계·계약의 작성·전송·본문·첨부·회신 목록은 후속 기능으로 분리한다.

### Key Entities *(include if feature involves data)*

- **프로젝트**: 팀의 공유 공간. 이름, 짧은 설명, 생성자, 생성 시각을 가진다.
- **프로젝트 멤버십**: 회원의 프로젝트 배정과 관리 담당자 여부를 나타낸다. 한 회원은 같은 프로젝트에서 하나의 유효 멤버십만 가진다.
- **멤버십 변경 기록**: 누가 어느 회원을 어느 프로젝트에 추가·제외했는지 보존한다.
- **회원**: 기존 인증 기능의 내부 회원. 승인 상태와 연결된 로그인 수단을 가진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 승인 회원은 별도 관리자 도움 없이 2분 안에 프로젝트를 만들고 자신의 룸에 들어갈 수 있다.
- **SC-002**: 승인 대기 회원의 생성·입장, 미배정 회원과 미배정 서비스 관리자의 룸 입장, 일반 회원과 타 프로젝트 관리 담당자의 무권한 멤버 변경 시도에서 허용 0건이다.
- **SC-003**: 프로젝트 관리 담당자가 승인 회원을 추가·제외하면 두 회원의 다음 프로젝트 목록·룸 접근 결과가 변경된 배정과 일치한다.
- **SC-004**: 내부 팀원 4~5명이 각자 자신의 배정 프로젝트만 선택 화면에서 확인하고, 관리 담당자는 추가 설명 없이 멤버 배정 화면을 찾아 사용할 수 있다.
- **SC-005**: 같은 회원의 Google·Discord 재로그인에서 프로젝트 배정 차이와 중복 멤버십이 0건이다.

## Assumptions

- 기존 Google·Discord 로그인, 서비스 가입 승인, 최초 관리자 지정 기능을 사용한다. 가입 승인과 프로젝트 배정은 별개다.
- 서비스 관리자는 모든 프로젝트의 배정 작업에 필요한 최소한의 프로젝트 정보와 멤버 현황을 볼 수 있다. 이 관리 화면은 룸 콘텐츠 열람 권한을 부여하지 않는다.
- 프로젝트 관리 담당자 추가 지정·양도, 관리 담당자 제외, 프로젝트 삭제, 회원의 자발적 탈퇴는 이번 범위 밖이다.
- 인수인계·계약 목록과 중복 계약 탐색은 다음 기능이다. 이 기능의 성공만으로 원본 명세 R20의 본문·첨부 차단 전체를 검증했다고 판정하지 않는다.
- 멤버십 변경으로 미완료 요청의 담당자가 접근 권한을 잃는 경우의 후속 처리는 요청 기능 구현 시 원본 명세의 담당자 이탈 규칙에 연결한다.
